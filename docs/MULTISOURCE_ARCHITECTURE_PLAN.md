# Модули источников и развитие интерфейса SearchCar

Дата: 30 сентября 2026 года; дополнено 5 октября. Статус: проект плана для обсуждения.
Изменения приложения и миграции этим документом не запускаются.

## 1. Цель и исходные решения

Новый сайт подключается собственным модулем, который знает его ссылки,
поиск, карточки, цены и признаки доступности. Проекты, очередь, история,
избранное, резервные копии и основная структура интерфейса остаются общими.
Специфичная функция сайта расширяет свой модуль и предусмотренные места UI.

Предлагаемая первая версия — **модульное приложение с модулями в составе
релиза**. Используем существующие Python backend, React frontend и Tauri;
не вводим микросервисы, отдельную БД для каждого сайта или загрузку чужого
исполняемого кода. Модульность кода и независимый выпуск плагинов — разные
задачи: для первого варианта не нужен магазин расширений.

Согласовано с пользователем 30 сентября:

- один поисковый проект относится к одному сайту; первоначально рассматривались
  смешанные списки. Уточнение 5 октября ниже заменяет этот вариант рабочими
  областями отдельных сайтов;
- новые модули добавляют разработчики через обновление приложения;
- следующий сайт — [Copart](https://www.copart.com/); до проверки реальных
  данных и доступа окончательный контракт его модуля не фиксируем;
- основной сценарий Copart — находить машины, показывать сведения о них и
  заметно отображать запланированный аукцион. Для Copart создаём собственные
  карточку и страницу автомобиля: однократно копируем текущую разметку как
  основу и адаптируем внутри модуля. Не расширяем компоненты Encar аукционными
  параметрами. Текущий дизайн остаётся основой для будущих похожих на Encar
  сайтов; детали дизайна Copart предстоит проработать;
- Уточнение 07.10.2026 заменяет прежний план раздельных карточек аукционов:
  IAA/Copart используют общую AuctionCarCard, независимо от Encar. Адаптеры,
  нормализация статусов и подробные страницы остаются в модулях источников.
  Ранее описанная независимость композиций не требует дублировать эту карточку.
  См. [макет v3](mockups/auction-cards-v3.html) и [матрицу состояний](AUCTION_CARD_STATES.md).
- аккаунта Copart и доступа к CSV у пользователя сейчас нет; способ подключения
  пока не выбран, нельзя строить первый модуль на предположении о таком доступе;
- macOS Apple Silicon и Windows x64 получают одинаковые возможности;
- русская и украинская локализации остаются обязательными.

Объединение сайтов внутри проекта пользователь допускает в будущем, сейчас
оно исключено из реализации. Для этого в будущем можно выделить `ProjectSearch`:
проект содержит несколько поисковых конфигураций, каждая со своим источником,
ссылкой, фильтрами и прогрессом. Сейчас храним одну конфигурацию на проект,
передаём её адаптеру явно и не привязываем идентичность объявления к проекту.
Это оставляет путь миграции без лишней сущности в первой версии.

Уточнения 5 октября: следующие источники — **Copart USA и IAA USA**, только
публичные данные без аккаунтов. Выделяем семейства «Площадки» и «Аукционы»,
не дублируя проекты и общую инфраструктуру. Сценарий аукционов включает выборку
на сегодня по часовому поясу компьютера и Telegram-публикацию после поиска.
Канал задаётся у проекта; сообщение — фото, краткие характеристики, дата/время
и ссылка. Подтверждены публикации только ещё не опубликованных лотов,
отдельные уведомления о переносе и пометка, если время начала прошло.
Хранение пока обсуждается. Рабочие экраны группируем по сайтам;
дизайн/навигацию согласуем отдельно:
[SOURCE_NAVIGATION_UX_PLAN.md](SOURCE_NAVIGATION_UX_PLAN.md).
Актуальные этапы, ограничения и открытые решения описаны в
[плане аукционного мониторинга](AUCTION_MONITORING_PLAN.md); он уточняет
прежний Copart-only сценарий этого документа.

## 2. Что показал разбор текущего кода

| Участок | Текущая зависимость | Что необходимо изменить |
| --- | --- | --- |
| `backend/app/scanner.py`, `parser.py` | Селекторы Encar, корейские признаки, KRW, формат ссылок | Выделить алгоритм Encar и нормализацию его данных |
| `backend/app/worker.py` | Прямые вызовы scanner/parser, `_encar_detail_reader`, `source_key="encar"`, locale `ko-KR` | Получать адаптер для конкретного проекта/объявления |
| `backend/app/detail_workers.py` | Уже есть фабрика чтения и `source_key`, но результат — свободный dict | Сохранить пул, дать его границе типизированные задачи и результаты |
| `models.py`, `services.py` | Уникальный `canonical_encar_id`, глобальные alias, KRW-поля | Идентичность объявления в пределах источника, валюта и вид цены |
| `main.py`, `schemas.py`, `external_links.py` | Проверки Encar, ссылки, API-поля `encar_id`, доступ к источнику зафиксирован | Общая валидация и API с явным источником |
| `vehicle_groups.py`, `reporting.py` | Корейские номера, группировка отчёта по номеру/Encar ID | Исключить объединение разных источников по совпавшему ID или номеру |
| Изображения и импорт | Пути `cars/<encar-id>/…`, доступ к файлу через Encar ID | Адресация через внутренний ID, совместимость старых файлов |
| `app/page.tsx` | Около 4 800 строк: экраны, типы, формы, KRW и Encar-подписи вместе | Разделять по функциям и выделить общие компоненты без редизайна |
| CSS и desktop entry | Общие CSS; desktop импортирует тот же `app/page.tsx` | Сохранить общую UI-базу, изолировать стили расширений |
| Лицензии | Уже есть каталог источников и `sources` в лицензии | Использовать существующий механизм, убрать жёсткий `encar` в постановке и исполнении jobs |

Поэтому замена только parser не решит задачу: затронуты идентичность,
хранение, очередь, разрешения и отображение. Старые документы текущего плана
местами отражают прежний этап реализации; источником технических выводов
для этого плана служит текущий код.

## 3. Границы модулей

Реализация 11.10.2026 (MSA-08, срез 8): Python/React используют общий build-time
каталог `backend/app/sources/catalog.json`; явные backend factories и frontend
UI entries остаются независимыми от метаданных. Нет фиксированного списка
трёх сайтов в навигации, запуске или сохранении разделов. Новая площадка может
подключить свою композицию, а аукцион — общую семейную. Encar пока сохраняет
старую композицию внутри page.tsx; перенос без редизайна не объявляется завершённым.
Порядок и границы добавления: [SOURCE_MODULE_REGISTRATION.md](SOURCE_MODULE_REGISTRATION.md).

| Часть | Ответственность | Не должна делать |
| --- | --- | --- |
| Модуль сайта | Проверять URL, получать выдачу/карточку, распознавать блокировки, нормализовать сведения | Писать напрямую в БД, менять статусы других проектов, определять права пользователя |
| Общий поиск | Планировать операции, учитывать режим и охват, отмену, лимиты, ошибки, прогресс | Знать CSS-селекторы, корейские тексты и параметры URL конкретного сайта |
| Данные и события | Проверять результат, сохранять наблюдения и историю, объединять надёжные поля | Считать сетевой сбой подтверждённой продажей |
| Общий UI | Навигация, проекты, история, базовые элементы управления, форматирование, общие фильтры | Навязывать всем источникам одну композицию карточки/страницы, разбирать сырой ответ сайта или решать права доступа |
| Семейства площадок/аукционов | Общие для семейства нормализованные правила и UI-блоки: цена/доступность либо даты/раунды/выборка на сегодня | Разбирать селекторы конкретного сайта или дублировать очередь и таблицу проектов |
| Telegram | Настройка бота, очередь доставки и журнал публикаций после поиска | Читать источник самостоятельно или превращать ошибку доставки в ошибку поиска |
| UI источника | Собственные карточка и страница автомобиля, поля проекта, локализация и локальные стили; повторное использование базовых элементов по необходимости | Менять глобальные стили, очередь, карточку или страницу другого источника |
| Функциональный модуль | Например, сравнение или экспорт поверх общего API | Импортировать парсер сайта для получения данных |

Зависимости идут от адаптера к общим типам и от экранов к публичному API.
Модуль Encar не импортирует модуль другого сайта. Реестр содержит явный список
встроенных модулей; выбор происходит по проверенному ключу и URL, а не имени
Python-модуля из пользовательского ввода.

### Время жизни браузера аукционов — 18.10.2026

`BrowserRuntimePool` принадлежит одному последовательному worker-потоку.
Адаптер явно включает `reuse_browser_session`; его runtime предоставляет
`park()` (локальный about:blank, прекращение polling прошлого поиска),
`reuse_requested()` (профиль не запрошен окном выбора и браузер не закрыт)
и идемпотентный `close()`. Sync Playwright объекты не передаются в поток выбора.
Уточнение18.10: IAA задаёт `reuse_windowed_browser_session=False`.
`has_window` учитывает и открытое, и свёрнутое окно: такой runtime закрывается
при освобождении задания вместо park/idle-кэша. Полностью headless IAA остаётся
переиспользуемым. Политика остальных источников и показ окна во время поиска
этим уточнением не меняются.
Ни фильтры, ни результаты не кэшируются в pool: каждая job использует frozen
план проекта, повторную навигацию и source guard, прежние listeners удаляются.

Ключ кэша — owner/source/browser options; смена owner/options закрывает старый
контекст. До двух idle runtime хранятся не более десяти минут, затем закрываются;
shutdown закрывает все. Перед Encar/другим адаптером без reuse idle-кэш
освобождается, чтобы не расширять существующий бюджет detail workers.
Выбор фильтров запрашивает уступку source-profile lease; worker освобождает
только idle runtime, а выбор отменяемо ждёт до30сек. Активный поиск не закрывается
другим потоком. Контекст выбора пока не передаётся worker: первый поиск после
выбора всё ещё может потребовать отдельную ручную проверку.

Обычная навигация/пагинация скрыта. Обнаруженная промежуточная проверка получает
один пассивный бюджет8сек на поиск без новых запросов/кликов. Это не retry для
голого403/429 и не обход CAPTCHA. Видимое окно открывается только для
неразрешённого manual prompt/существенного consent; явный безопасный отказ
необязательных cookies сохраняется. После ручной проверки сохраняется тот же
контекст, а не новый headless. Отказ macOS минимизировать окно обозначается
MANUAL_MINIMIZE; результат не выдаётся за полностью скрытый поиск.

Классификация ручного challenge принадлежит адаптеру. IAA не считает скрытый,
прозрачный или1px служебный iframe запросом действия пользователя; проверяет
размер содержимого (без рамки) и видимость iframe/предков. Видимый challenge
блокирует чтение и поверх существующей таблицы. Явная инструкция проверки
отличается от надписи reCAPTCHA; отказ доступа не становится успешной пустой
выдачей. Общие collector/selection используют прежние manual_required/blocked,
без IAA-селекторов в worker или UI.

Предлагаемое расположение, уточняемое при реализации:

## 4. Контракт источника

Первый контракт следует существующей цепочке поиска; не проектируем
универсальный язык сценариев или конструктор произвольных форм.

- **Описание источника:** стабильный `source_key`, семейство площадка/аукцион,
  название, версия адаптера,
  поддерживаемые домены и доступные возможности.
- **Ссылки:** распознавание поисковой/прямой ссылки, проверка, нормализация,
  получение строкового ID. Не требуем цифровых ID или страниц вида `page=2`.
- **Настройка поиска:** проверенная конфигурация, применение поддерживаемых
  фильтров и разрешение режима. Если диапазон цены нельзя применить на сайте,
  интерфейс явно отличает локальную фильтрацию от поиска по этому диапазону.
- **Чтение выдачи:** последовательность порций результатов с курсором,
  строками объявлений и доказательством конца. Общее число может быть неизвестно.
  Порция может происходить из страницы, API либо файла. Для файла фиксируем
  идентификатор/дату снимка и применённую выборку; не называем импорт CSV
  просмотром страниц сайта. Backend сообщает доступные варианты охвата.
- **Чтение объявления:** полные сведения и, при поддержке источником,
  облегчённая проверка цены/доступности. Не передаём ORM-объекты в браузерный поток.
- **Сеанс:** открытие и закрытие принадлежащего модулю браузерного контекста
  либо клиента; отмена и таймаут обязательны.
- **Ошибки:** общий код, область действия (объявление/проект/источник),
  возможность повтора, диагностические сведения без секретов.

Пример возможностей: поиск по ссылке, прямое наблюдение, цена в выдаче,
облегчённое чтение, фильтр цены на сайте, фотографии, страховая информация.
Статические возможности дополняются доступностью данных конкретного объявления:
наличие фото у источника не означает, что оно есть у каждой машины.

Результат содержит источник и ID, канонический URL, время получения и время
данных источника (если доступно), доступность с основанием, денежные значения
с валютой/назначением, нормализованные
характеристики и список фактически прочитанных полей. «Не прочитано» отличается
от «проверено и отсутствует»: быстрый режим не обнуляет ранее известные детали.
Сырой текст и специфичные данные хранятся отдельно с версией формата.

Контракт включает `contract_version`; в запуске фиксируем версию приложения
и адаптера. Несовместимый/неисправный модуль получает понятное состояние,
сохранённые данные остаются доступными. Импорт адаптера выполняется управляемо:
ошибка его инициализации не должна ломать загрузку общего каталога источников.

Реализованный минимум MSA-04 (09.10.2026): `sources/contracts.py` задаёт
описание, ссылочную идентичность, результат сбора и интерфейс адаптера;
`sources/registry.py` держит независимый каталог и ленивую явную загрузку.
`sources/encar.py` переиспользует прежний parser/scanner. Worker обращается
к контракту, но выбор проекта остаётся Encar до миграции MSA-05/06.
Прежние нормализованные значения возвращаются с дополнительным
`source_observation` (происхождение, режим/неизвестные поля, деньги KRW и
назначение суммы). Это provenance последнего чтения, а не утверждение,
что сохранённый полный профиль был заново прочитан при PRICE_STATUS.
В payload запуска сохраняется `execution_versions`; старые endpoint-поля
и таблицы совместимы. Будущие адаптеры не считаются реализованными этим
интерфейсом: даты/точность, разные валюты и поля аукционов добавляются с
проверками реального разрешённого источника.

## 5. Идентичность, цены и миграция

### Объявление и автомобиль

Существующую таблицу `cars` на первом этапе сохраняем, но считаем запись
объявлением сайта. Её внутренний `id` и все связи с историей остаются прежними.
Внешняя идентичность — уникальная пара `(source_key, source_listing_id)`.
Alias тоже получает источник; одинаковый ID двух сайтов создаёт две записи.

**Согласовано 10.10.2026:** одинаковые названия проектов разрешены на разных
сайтах. Уникальность названия — `(owner_id, source_key, name_key)`; поиск по URL
также ограничен владельцем и источником. Одно объявление одного сайта может
участвовать в нескольких проектах, сохраняя один внутренний ID и независимые
отметки ProjectCar. Alias обязан относиться к объявлению того же источника.

**Уточнение реализации 17.10.2026 — пресеты поиска:** проект дополнительно
хранит versioned `search_config` без браузерных секретов. Уникальность поиска —
`(owner_id, source_key, search_identity)`: для прежних URL-проектов это стабильный
hash исходного URL, для IAA-пресета — hash нормализованных публичных условий.
Нативная ссылка может не отражать сортировку либо содержать другой курсор;
она не является идентичностью условий. Разные конфигурации могут иметь один
URL, а другая страница/размер не создают второй такой же IAA-проект.
SQLite12/Alembic0021 сохраняют прежние ID/связи; SQLite делает проверенный
pre-migration backup и проверку FK под общей блокировкой миграций.
В очередь передаётся независимая копия конфигурации. Capture/finalize/identity/
restore/verify принадлежат адаптеру; общий coordinator/worker не перечисляет
сайты или их селекторы. Encar остаётся в прежнем URL-режиме и дизайне.

**Согласовано 10.10.2026 — фото:** храним одну текущую локальную MAIN-копию
без истории изображений. Удаляем файл только при окончательном удалении записи
объявления; удаление одного проекта/связи не удаляет общую копию. При ошибке
нового screenshot сохраняем прежний исправный файл. Способ получения остаётся
согласованным screenshot области основного фото выдачи через общую очередь;
разрешённость доступа/публикации — отдельный gate, не обходится screenshot.

Физически одна машина может продаваться в нескольких объявлениях. Это отдельная
группировка для показа; она не сливает цены, статусы и историю объявлений.
На первом этапе группируем внутри источника. Межсайтовое сопоставление по VIN
проектируем отдельно. Совпадения названия, цены, фото или номера без страны
недостаточно; продажа на одном сайте не означает продажу на другом.

### Денежные значения и характеристики

- Цена: сумма целым числом в минимальных единицах, код валюты и основание
  (`SALE_TOTAL`, `RENT_MONTHLY`, `LEASE_MONTHLY`); «по запросу» — отдельное
  состояние, не ноль. KRW мигрирует без изменения числовых значений.
- Для аукциона возможны одновременно `CURRENT_BID` и `BUY_NOW`; оценочная
  стоимость — самостоятельная величина `ESTIMATED_RETAIL`, не цена продажи.
  Нужен набор типизированных денежных значений, а не одна сумма, которая
  меняет смысл от экрана к экрану. `current_price` на переходный период —
  совместимое представление Encar, не единственное хранилище Copart.
- Валюта и основание сохраняются также в снимках, истории, отчётах и фильтрах.
  Изменение валюты/типа предложения не рисуем как обычный процент изменения.
- При нескольких валютах сортируем по цене внутри валюты либо предлагаем
  выбрать валюту. Конвертацию и сравнение полной цены с месячным платежом
  в первый этап не включаем.
- Общие характеристики имеют коды и единицы; словарь сайта сопоставляет
  исходные значения с ними. Тексты RU/UK формируются при показе. Неизвестное
  значение сохраняется в оригинале, не подменяется догадкой.
- Сайтоспецифичные поля находятся в `source_data` с версией; часто фильтруемые
  общие поля типизированы, а не спрятаны в произвольный JSON.
- История котировок разделяется по назначению и валюте; для ставок также по
  проверенному раунду торгов. Повторные торги не превращают сброс ставки
  в событие «авто подешевело». Общий формат события поддерживает код,
  источник, прочитанные изменения и ключ локализации; незнакомый код имеет
  безопасный общий показ, а не требует новой ветки для каждого сайта в worker.

### Последовательность миграции

1. Backup и проверка свободного места; остановка записи/поиска на время миграции.
2. Добавить источник проектам/объявлениям/alias, заполнить существующие записи
   значением `encar`; внешний ID взять из текущего canonical ID, не из
   отображаемого регистрационного номера сайта.
3. Проверить заполнение и коллизии, создать новые составные ограничения.
   На исходной схеме `canonical_encar_id` обязательно и глобально уникально.
   10.10.2026 migration SQLite 9 / Alembic 0018 сняли NOT NULL/старое
   ограничение: для Encar оно совпадает с source listing ID, для других сайтов
   равно NULL; это защищено CHECK. Фиктивные Encar ID не допускаются.
4. Перевести чтение/запись на общие поля. Для старых отчётов и импортов оставить
   ограниченный слой совместимости, явно трактующий их как Encar. Зафиксировать
   условие удаления этого слоя отдельной задачей.
5. Новые фото хранить по внутреннему ID объявления. Старые пути сохранить
   читаемыми через текущие метаданные; проверить выдачу файлов, backup и перенос
   между Windows/macOS, включая разделители пути и права владельца данных.
6. Проверить старые backup, SQLite миграции, PostgreSQL/Alembic и конвертер.
   Отсутствующий модуль после восстановления блокирует поиск только этого
   источника, не просмотр его истории.

Откат после изменения схемы — восстановление проверенного backup совместимой
версией приложения, а не запуск старого бинарника поверх новой БД.

### Copart: что уже известно и как это влияет на модель

Ниже — проектные решения по официальной справке Copart, проверенной 30 сентября.
Доступ к реальному аккаунту, данные CSV и поведение лотов в приложении ещё
не проверялись. Базовый охват предлагаем ограничить Copart USA; другие регионы
не считаются автоматически поддержанными по совпадению бренда.

| Отличие | Предлагаемое решение SearchCar |
| --- | --- |
| Ставка и Buy It Now могут существовать одновременно | Две подписанные суммы, независимые истории/фильтры; показываем время получения |
| Продажа может требовать подтверждения продавца | Разделить доступность объявления, фазу торгов и условия продажи; `On Approval` как условие не означает, что торги уже закончились |
| Лот может попасть на повторные торги | Хранить события переноса/нового раунда; не считать окончание таймера доказательством продажи |
| Сведения о повреждениях, документе и пробеге имеют собственные коды | Локальный словарь Copart, исходное значение сохраняется; неизвестное не превращается в «без повреждений» |
| Аукционная дата привязана к часовому поясу | Хранить UTC и исходный пояс/точность, показывать время пользователя и пояс; неизвестную дату не заменять фиктивным таймером |
| Полный VIN может отсутствовать | Хранить доступный VIN и признак полноты, не использовать маскированный VIN для склейки |

Пользователь уточнил основной сценарий: найти подходящие машины, изучить их
и понимать, когда состоится аукцион. Для первого Copart-модуля предлагаем
приоритеты: поиск лотов → характеристики/фото → дата и состояние торгов →
периодическое обновление этих сведений. Текущая ставка и Buy It Now показываются
при наличии данных; отслеживание каждого изменения ставки не является
согласованной целью. Автоматические ставки, покупки, логистика и расчёт комиссий
в этот сценарий не входят. Периодическая выборка не обещает актуальную ставку
в реальном времени или обнаружение каждого промежуточного повышения.

Нормализованные фазы торгов — предложение нашей модели, не обещание наличия
таких API-кодов у Copart: назначены / идут / завершены / результат неизвестен.
Подтверждение продавца и итог продажи сохраняются только по прочитанным данным.
Время истекло, лот исчез или ответ требует авторизации — недостаточные основания
для `SOLD`. Возврат ранее завершённого лота в новой выдаче должен обрабатываться;
правило Encar «проданные не проверяем напрямую» не переносим на аукцион вслепую.

Пробег хранится с исходной единицей и признаком достоверности; показ в километрах
не стирает исходные мили. Год модели отличается от даты первой регистрации.
Для фильтров Copart нужен явный выбор «Текущая ставка» / «Buy It Now», поскольку
ограничение ставки не ограничивает окончательную стоимость покупки.

Основания: [способы покупки](https://www.copart.com/help/bidding-and-buying/ways-to-bid-buy),
[повторные торги](https://www.copart.com/help/bidding-and-buying/bidding-buying-faq),
[термины и значения полей](https://www.copart.com/help/finding-vehicles/glossary-of-common-terms-used-at-copart).

### Copart: способ получения данных проверяем до написания парсера

Copart описывает официальный **CSV Sales Data**, обновляемый каждые 15 минут,
с данными лотов и торгов. Это кандидат для получения общей выборки: один
снимок можно обработать локально для нескольких проектов. Но наличие нужных
ставок, фотографий, полнота, доступ аккаунта и допустимость нашего применения
ещё не подтверждены. Интервал файла не равен гарантии свежести каждого поля.
Источник: [CSV Sales Data](https://www.copart.com/Content/US/en/buyer/Sales/Download-Sales-Data).

В [условиях сайта, раздел 6](https://www.copart.com/content/us/en/terms-of-use)
оговорено коммерческое использование контента, а в
[Image and Data License Agreement](https://www.copart.com/Content/US/EN/buyer/Sales/Image-and-Data-License-Agreement)
описаны ограниченные права и получение лицензируемых материалов через CSV.
Из этих документов нельзя заключить, что любое копирование карточек и фото
разрешено для нашего desktop-продукта. Перед выпуском Copart нужно подтвердить
подходящий способ и условия доступа; конкретные права не считаем установленными
одним фактом наличия аккаунта.

У пользователя нет аккаунта и доступа к CSV. Поэтому файл остаётся кандидатом,
а не выбранным способом интеграции. Начинаем с изучения доступных без входа
полей реальных поисковых страниц/лотов и условий их использования; отдельно
выясняем, что потребуется для официальных данных. Аккаунт автоматически
не создаём, необходимость его появления включаем в результат исследования.

Короткий исследовательский этап: проверить варианты доступа к данным, при
получении доступа изучить реальную схему CSV, выбрать транспорт и правила
свежести, проверить покрытие нужных полей.
Если CSV не покрывает задачу — проверить предоставляемый Copart вариант
интеграции/согласованный доступ. Не объявляем внутренние запросы сайта
официальным API. Если потребуется платный доступ, отдельно оценить стоимость
до включения его в согласованный план без обязательных регулярных расходов.

При выборе файла адаптер отдаёт наблюдения из снимка, а UI показывает
«Данные источника на …». Файл устарел или не загрузился — не массовая продажа.
Отсутствие лота в таком файле не доказывает его продажу: сначала проверяется
охват файла и наличие допустимого способа дополнительной проверки.
Если доступ требует входа, аутентификация источника отделяется от лицензии
SearchCar; секреты хранятся локально защищённо и не входят в обычный backup.
При истечении сеанса появляется действие восстановления входа без потери данных.
В этой работе вход в аккаунт, скачивание CSV и запрос доступа не выполнялись.

## 6. Поиск, доступы и изоляция сбоев

Общий координатор выбирает адаптер для каждого проекта и прямого объявления.
Быстрый/точный режимы сохраняют понятный смысл, но план операций учитывает
возможности сайта. Если надёжной цены в выдаче нет, быстрый режим не обещает
обновление цены без чтения карточки; недоступный режим нельзя включить незаметно.

Для Encar сохраняем согласованное поведение: найденные известные объявления
обновляются по выдаче, отсутствующие перепроверяются по прямой ссылке после
полного обхода, подтверждённо проданные не расходуют время поиска. Первая
страница не даёт основания считать отсутствующими все остальные машины.

Полнота результата относится к выбранному охвату конкретного проекта/источника.
Для курсорного поиска с неизвестным итогом показываем количество пройденных
порций/объявлений и спиннер; не выдумываем «страницу 2 из 2» или 100%.

Сохраняем существующий предел 1–2 detail workers; это чтение карточек внутри
одного поиска, а не число одновременно работающих проектов/сайтов.
Расширение этого пула — задача PAR-2.
Есть общий бюджет ресурсов устройства и отдельный лимит каждого источника.
Один источник делит лимит между выдачей, деталями и всеми своими проектами.
Контексты, cookies и сеансы источников не смешиваются. Блокировка/CAPTCHA
останавливает обращения к соответствующему источнику; другие разрешённые
источники продолжаются, итог запуска отражает частичный результат.

Доступ проверяется при создании/редактировании проекта, постановке поиска и
его фактическом запуске, включая планировщик и прямые объявления. Источник
определяется сервером по сохранённой конфигурации и URL. Для смешанного запуска
недоступные проекты явно отмечаются как пропущенные с причиной, остальные
продолжаются. Используем существующие entitlements, не отдельную систему лицензий.

Уточнение 10.10.2026: состав сайтов также управляется подписанной лицензией.
Если ограничение источников отсутствует либо задан wildcard, ключ разрешает все
адаптеры, поставленные и включённые в текущей версии приложения. Явный список
задаёт subset, пустой список запрещает поиск по всем сайтам. Ежедневное штатное
обновление lease одновременно обновляет этот список; отдельный канал конфигурации
не вводим. Отзыв сайта блокирует новые и ещё не начатые работы, но не удаляет
локальные проекты, машины или историю. При отсутствии сети действует только
последняя проверенная подписанная lease до её штатного срока действия.

Браузерные переходы, загрузка медиа и внешние ссылки проверяются по доменам
модуля, включая согласованные CDN и редиректы. Данные сайта не могут указать
произвольный локальный путь, внутренний адрес или исполняемый код для запуска.

Такая архитектура изолирует ожидаемые ошибки и зависимости кода, но не является
песочницей: авария общего backend затронет приложение. Отдельные процессы
рассматриваем, если реальные сбои второго адаптера потребуют этого, а не
обещаем абсолютную независимость модулей внутри одного процесса.

### 6.1. Области запуска и координация — уточнение 08.10.2026

**Подтверждено:** пользователь должен запускать один/выбранные проекты, все
проекты конкретного сайта и несколько/все сайты. Межсайтовая команда не меняет
правило «один сайт на проект» и не объединяет рабочие экраны. Далее — предложение
механики, не уже реализованное поведение.

**Исходное состояние перед MSA-06:** `job_queue.claim_next_job` атомарно разрешает только
один активный `ScanRun` во всём приложении. `worker.process_job` проходит проекты
последовательно и использует Encar-контекст с `ko-KR`; `_detail_worker_count`
выбирает 1/2 читателей карточек. Ручной `enqueue` отклоняет пересечение с активными
проектами и поглощает их ожидающий автоматический поиск. `enqueue_scheduled`
пока подавляет новый автоматический запуск при любом активном job владельца.
Следовательно, две кнопки сайтов сами по себе не дадут ни изоляции сеансов,
ни одновременного поиска; общий диспетчер нужно изменить в MSA-06.

**Backend-срезы 2–5 реализованы 10.10.2026:** общая граница enqueue обслуживает
ручной поиск и планировщик, фиксирует проектные планы и исключает занятые части.
Смешанная партия чередует сайты по одному проекту, начиная с их первого
появления в выбранном списке; порядок проектов внутри сайта не меняется.
Worker поддерживает такой же порядок для legacy job, собственный runtime
каждого сайта и адресную отмену. Отдельные партии остаются FIFO, без прерывания
текущего job; одновременно работает один проект с прежним бюджетом 1/2 detail
readers. Доступность новых сайтов этим не подтверждается: проверка смешанного
исполнения выполнена на fake-adapters; реально поставлен только Encar.
**Срез 6 реализован локально:** missing/wildcard signed policy разрешает
поставленные модули; explicit subset/empty ограничивает доступ. Штатная проверка
при старте и каждые 6 часов обновляет права без нового кода активации. Enqueue
проверяет реальные источники owned проектов/машин и frozen plans; планировщик
сохраняет выбор запрещённых проектов, но не запускает их. Worker повторяет
проверку перед каждым проектом и сохраняет явную причину отзыва, продолжая
разрешённые части партии. Нормальная смена прав между preflight и enqueue не
останавливает worker. Локальные проекты/история и сроки offline lease сохранены.
Сервису подготовлена миграция 0006 с сохранением старых явных ограничений и
переключатель «Все сайты, включая новые»; выдаётся backward-compatible explicit
signed list. Рабочий сервис/D1 ещё не обновлены этим локальным срезом.

**Общий путь постановки:** проект → сайт → все сайты — три способа выбрать
проекты для одной серверной границы. Backend сам проверяет владельца,
`source_key`, доступность модуля и лицензию; повторяет проверки перед исполнением.
Состав и конфигурацию запуска фиксируем при постановке: переключение UI или
сохранение настроек не должно менять уже выполняющийся поиск.

Сначала переиспользуем `ScanRun` и `ProjectScanRun`: общий запуск и независимые
результаты его проектов, сгруппированные по сайту при отображении. Не вводим
второй worker/планировщик/историю для каждого модуля. Достаточность нынешних
сущностей подтверждаем тестами до миграции; область отмены хранится явно.

**Защита от конфликтов:**

- не более одного ожидающего/выполняющегося поиска того же проекта. Проверка
  и постановка атомарны, включая одновременные ручной запрос и тик планировщика;
- в массовой команде занятые проекты не дублируются; остальные можно поставить
  в очередь. Пользователь видит ссылку на существующий запуск и причины пропусков;
- сохраняем смысл нынешнего ручного поглощения ожидающей автоматической задачи;
  работающий поиск не прерывается скрыто. Другую конфигурацию не объединяем
  молча: показываем уже поставленные параметры и требуем отдельного решения;
- повторные тики планировщика не накапливают одинаковые задачи. Занятый Encar
  не должен мешать постановке свободного IAA, даже если исполнение пока ждёт;
- каждый сайт получает собственные browser context/client, cookies, locale,
  курсор пагинации, таймауты и сигнал отмены. Общим может быть процесс браузера,
  но не изменяемая страница или ORM Session в разных потоках;
- один бюджет устройства и лимит источника охватывают все его проекты,
  выдачу, детали и медиа. Нельзя дать каждому из трёх сайтов отдельный полный
  пул и незаметно умножить нагрузку;
- блокировка/CAPTCHA/429 применяются к соответствующему сайту: обращения к нему
  останавливаются/ожидают по подтверждённой причине; остальные разрешённые
  сайты продолжаются. Ошибка одной машины не обязательно блокировка сайта;
- результаты фиксируются независимо по проектам. Полнота и исчезновение
  проверяются только относительно его охвата; совпавший ID другого сайта не
  перезаписывает машину. Сбой/отмена одной части не откатывает успешные части;
- отмена проекта, части сайта и общего запуска адресует разные наборы задач.
  Уже сохранённые результаты/отправленные сообщения не удаляются. Сон, выход
  и перезапуск оставляют явные прерванные состояния и освобождают занятые ресурсы.

**Политика исполнения — подтверждено 09.10.2026:**

1. Выбранный вариант: можно поставить все сайты сразу, но выполнять
   один проект за раз с нынешними 1–2 detail workers. Для смешанной партии
   чередовать сайты на границе проектов, сохраняя порядок проектов одного сайта.
   Нет переключения посреди страницы. Большой текущий проект всё равно задержит
   следующий сайт; очередь не выдаём за настоящее параллельное выполнение.
2. Отложено, не входит в текущий этап: если позднее понадобится одновременное
   чтение разных сайтов, потребуется отдельный срез
   MSA-06 после общего координатора. До двух активных сайтов, не более одного
   проекта каждого, с общим ограниченным бюджетом браузерных операций, а не
   двумя независимыми пулами. Экономный режим остаётся последовательным.
   Числа/справедливость распределения подтверждаем замерами на обеих ОС.

Вариант 2 не выбран и не означает разрешения PAR-2 (>2 readers)
или PAR-1 (несколько проектов одного сайта одновременно). Ни одна политика
не обещает абсолютного отсутствия сбоев; это проверяемые ограничения.

Telegram остаётся отдельной очередью после фиксации результата поиска.
Уточнение22.10.2026: общий бот `@search_car_app_bot` по умолчанию, token только
в server secret. Durable outbox устройства сам хранит задания, планирует
интервалы по bot и bot+chat между своими проектами, сохраняет повторы/cooldown.
Общего серверного планировщика/очереди доставки нет: прежнее требование21.10
отменено. Relay аутентифицирует клиента, проверяет разрешённого получателя и
выполняет одну попытку, возвращая результат/429 без собственных повторов.
Независимые установки не синхронизируют бюджет; соблюдение суммарного лимита
не гарантируется, внешнюю нагрузку учитываем по429/retry_after. Тип
получателя private/group/supergroup/channel подтверждается Telegram и связывается

даёт полномочий на публикацию.429/retry_after распространяет сохранённый
cooldown в этом приложении; подготовленный client-side gate ещё не является sender.
Собственный бот — TG-OWN-BOT будущего плана, не обязательный onboarding.
Предложение: готовая подборка проекта не ждёт долгого поиска другого сайта;
момент публикации в массовом запуске нужно подтвердить перед MSA-17.
Общий канал не означает общий поисковый контекст: дедупликация публикаций
учитывает источник, лот, раунд, канал и событие; неопределённая доставка не
повторяется автоматически. Сбой Telegram не занимает поисковый слот.

**Проверки до закрытия MSA-06:** одновременная постановка одних проектов;

Сайты имеют собственные пункты навигации, но не отдельные копии приложения.

Уточнение 08.10.2026: у Encar и других «Площадок» сохраняется нынешний дизайн
**проектов и запусков целиком**. Аукционный макет этих экранов относится только
к Copart/IAA и будущим аукционам. Настройки можно пересмотреть отдельно; выделение
компонентов/общего API не является разрешением на редизайн площадок.

Смена сайта в существующем проекте с историей запрещена: предлагается создать
новый проект. Это предотвращает переинтерпретацию сохранённых машин и отчётов.
Обычная замена ссылки внутри сайта сохраняет текущую процедуру смены условий
поиска и сброса соответствующей базовой выборки.

Возможности сайта, отсутствие значения и отсутствие доступа по лицензии — разные
состояния. Неподдерживаемое поле не показываем; неизвестное значение обозначаем
«Нет данных»; недоступный источник объясняем через настройку доступа.

Места расширения: поля формы проекта, дополнительные фильтры, целая карточка
и целая страница автомобиля. Реестр выбирает реализацию по источнику в точке
отображения, а не через условия `если Copart` внутри компонентов Encar.

Для Copart допустимо однократно скопировать разметку и необходимые стили текущей
карточки/страницы, затем развивать их независимо внутри модуля. Это осознанное
дублирование представления, а не временный шаг к единой универсальной карточке.
Не добавляем в Encar аукционные props, слоты и переключатели ради Copart.
Базовые кнопки, иконки, форматирование и другие действительно одинаковые элементы
переиспользуем; общую крупную оболочку карточки или страницы не навязываем.

Не копируем вместе с разметкой загрузку, мутации, проверку разрешений, очередь
или сохранение данных: страницы используют общий API и доступные общие hooks.
Специфичные данные и поведение экрана Copart остаются в его модуле.
Будущие сайты с обычными объявлениями ориентируем на представление Encar;
выделять общую композицию для них будем при появлении реального второго
потребителя, без универсального конструктора экранов заранее.
Не принимаем HTML/JavaScript или CSS из ответа сайта.

### Предлагаемая карточка и страница Copart

Это проект UX, а не согласованный окончательный макет:

- Краткая карточка: фото, название автомобиля, проект/источник и номер лота;
  главная дополнительная строка — **«Аукцион: дата, время, часовой пояс»**.
  Затем кратко пробег/повреждения и подписанная ставка или Buy It Now,
  если они доступны. В истории сохраняем контекст проекта на заметном месте.
- Подробности: галерея и характеристики плюс заметный блок «Аукцион» с
  запланированным временем, площадкой, текущим состоянием и переходом на сайт.
  Ниже — повреждения, документы, доступные ценовые сведения, история наблюдений.
- Состояния блока даты: дата назначена / дата ещё не назначена / дата перенесена /
  запланированное время прошло, результат не проверен. «Торги идут» показываем
  только по данным источника; ход местных часов не подтверждает начало/завершение.
- Показываем локальное время пользователя с поясом; исходное время площадки
  доступно рядом в подробностях. Без подтверждённого пояса не конвертируем
  произвольно. Обозначаем время начала аукциона, не обещаем точное время выхода лота.
- Для Copart предлагаем сортировку «Ближайшие аукционы» и фильтры по дате,
  площадке и состоянию. Лоты без даты помещаются отдельно/в конце. Это локальные
  фильтры сохранённых данных, если источник не поддерживает их при поиске.
- При смене даты обновляем карточку и сохраняем событие переноса. Не стираем
  ранее известную дату из-за неудачного чтения; показываем время последней проверки.
- Выборка «Аукционы сегодня» и публикация после поиска входят в новый
  [план аукционов](AUCTION_MONITORING_PLAN.md). Полный календарь и повторные
  напоминания оставляем будущими улучшениями.

Общий визуальный язык Encar/Copart/IAA сохраняется, но избранное/история
показываются в контексте выбранного сайта. Не требуется одинаковая высота
карточек разных источников ценой сокрытия важных сведений. Для списка одного
источника сохраняем устойчивое выравнивание колонок.

Стили расширений — CSS Modules либо строго локальный контейнер источника.
Запрещены глобальные правила для `button`, `input`, `.card` из модуля.
Общие цвета, размеры и компоненты находятся в общей UI-базе; изменение общей
базы по определению влияет на все источники и требует их регрессионной проверки.
Ключи кеша запросов/настроек включают нужный контекст пользователя, проекта и
источника; старые сохранённые UI-настройки переносим без сброса предпочтений.

Перед UI-реализацией отдельно согласуем макеты: боковая навигация и рабочие
области сайтов, создание проекта, карточка Copart с состояниями даты,
его подробная страница, варианты IAA, избранное/отчёт внутри сайта
и контрольное сравнение неизменённой карточки Encar.
Проверяем RU/UK, длинные названия, клавиатуру, узкое окно, loading/error/empty и
«источник отключён». Не строим универсальный конструктор дизайна.

Ниже — базовая последовательность выделения источников. Детальные этапы A0–A7

Тестовый адаптер на этапах 2–4 работает только на фикстурах: строковые ID,
другая валюта, неизвестное число страниц и отсутствующие возможности.
Он проверяет контракт, но не доказывает поддержку реального второго сайта.
Уточнение общих типов по его реальным требованиям допустимо и ожидаемо.

Обязательные проверки:

- одинаковый внешний ID у двух сайтов: отдельные записи, файлы и история;
- миграция существующих Encar-проектов, аренды/лизинга, alias, снимков и backup
  сохраняет внутренние ID и пользовательские отметки;
- ошибка инициализации/таймаут/CAPTCHA одного адаптера не блокируют исправный;
- отмена, сон, перезапуск, очередь планировщика и 1–2 workers на обеих ОС;
- полный и ограниченный поиск не дают ложных продаж и ложного успеха;
- частичное чтение не стирает цену/характеристики; суммы разных валют и типов
  предложений не попадают в одну числовую историю;
- недоступный по лицензии источник нельзя запустить через API/планировщик;
- общий интерфейс работает без дополнительных секций, а ошибка секции
  локализуется UI error boundary и сохраняет доступ к основной карточке;
- визуальная регрессия Encar при изменении другого источника; фиксированные
  колонки, анимации и фильтры остаются на согласованных местах;
- статические зависимости запрещают импорты между адаптерами и Encar-парсера
  в общем worker/UI; упаковка включает все зарегистрированные модули/словари;
- для Copart: ставка и Buy It Now не перезаписывают друг друга, перенос даты
  и новый раунд не создают ложных ценовых событий; неизвестный итог торгов,
  маскированный VIN, устаревший файл, мили и часовые пояса обрабатываются явно;
- часть текущих UI-тестов ищет функции внутри `page.tsx`: при разделении
  обновляем их на проверки поведения/рендера, не оставляем ложные проверки пути.

## 9. Объём, ограничения и вопросы

Это архитектурная задача высокой сложности: главный объём — миграция данных и
сохранение поведения, а не регистрация нового класса парсера. Первый полезный
результат — рабочий Encar за контрактом, следующий — мигрированные данные и
UI, затем реальный второй адаптер. Каждый этап имеет отдельный проверяемый
коммит; выпуск не требует завершить все будущие продуктовые функции.

Новые текстовые адаптеры/словари/React-секции обычно добавляют меньше размера,
чем уже поставляемый браузер; конкретный прирост измеряем на сборках. Если
сайту требуется другой движок или крупная зависимость, оцениваем это до выбора
реализации. Общий браузерный runtime поставляется один раз.

Не включаем сейчас: магазин сторонних плагинов, горячую замену кода без релиза,
межсайтовое склеивание автомобилей, пересчёт валют, расширение пула workers,
полностью настраиваемую схему интерфейса. При потребности в отдельных
устанавливаемых плагинах понадобится иной план: подписи пакетов, совместимость,
права, изоляция процессов, миграции и откат.

Осталось подтвердить публичный канал данных Copart/IAA без аккаунтов,
изучить примеры типичных поисков и проработать макеты карточки и подробностей
с акцентом на дату торгов.
Copart/IAA, один сайт на проект, модули в релизе, время компьютера и Telegram
после поиска подтверждены пользователем и повторного согласования не требуют.
Хранение и детали дизайна ещё обсуждаются; перенос опубликованной даты
сообщается отдельным уведомлением, исходный пост не редактируется.

До подтверждения каналов данных можно согласовать границы и подготовить этап Encar.
Обещать поддержку любого сайта одним неизменяемым контрактом нельзя: цель —
локализовать обычные изменения и заранее определить, какие требуют общей доработки.
