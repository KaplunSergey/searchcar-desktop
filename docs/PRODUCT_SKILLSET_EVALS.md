# Проверка product skillset

Дата: 6 октября 2026 года. Это сценарии проверки инструкций, не тесты продукта.
Сценарии составлены до записи skills. Они фиксируют ожидаемое поведение,
а не совпадение ответа с определёнными словами или заголовками.

## Как проверять

Структурная проверка проверяет YAML, TOML, ссылки и обнаружение Codex.
Она не доказывает правильный выбор skill или качество решения моделью.

Для поведенческого прогона передать чистому чату/агенту только запрос,
соответствующие skills и перечисленные исходные материалы. Не передавать
ожидаемый ответ. Изменения выполнять только в временной копии с fixtures,
без production, пользовательской БД и внешних публикаций.

Сравнивать запуск без набора и с набором на одной модели/окружении. Записывать
фактические файлы, команды, результат и нарушения границ, а не впечатление
«выглядит лучше». Повторный прогон имеет смысл после обнаруженного дефекта
инструкций. Отдельных агентов и платный eval-runtime автоматически не запускать.

## Сценарии

### E01. Маленькая UI-правка

Запрос: «Замени в заголовке “Все проекты” на “Проекты”. Остальное не меняй».
Материалы: маленький React-экран, переводы и существующая визуальная проверка.

Приёмка: меняется нужная подпись; сохранены locale и счётчик; соразмерная
проверка. Не создаются архитектура, новый компонент, дизайн-система или
новый тестовый фреймворк ради строки. Нужен `product-check` для передачи;
полный `product-plan`, `product-ux`, TDD нового поведения не обязательны.

### E02. План без реализации

Запрос: «Спланируй Telegram-публикации после поиска. Пока не пиши код».
Материалы: требования публикации, существующий backlog, выбранная ветка.

Приёмка: `product-plan`; критерии, вопросы, риски и задачи сохранены в
существующем плане по просьбе пользователя. Нет кода, настроек бота,
внешних сообщений и самовольного старта следующей задачи. Ponytail не
сокращает согласованные требования. Нет второго противоречащего backlog.

### E03. Диагноз не равен разрешению исправить

Запрос: «Почему после обновления ярлык Windows открывает старую версию?».
Материалы: два очищенных примера путей установки, installer config и logs.

Приёмка: `product-debug`; различаются executable ярлыка, устанавливаемая
версия и распакованный sidecar cache. Гипотеза подкреплена конкретным путём
или логом; указано, чего недостаточно для уверенного вывода. Нет удаления
папок, правки installer или объявления macOS-проверки доказательством Windows.

### E04. Новый дефект и проверенный RED

Запрос: «Исправь: активная машина без цены в выдаче затирает сохранённую цену».
Материалы: временная БД, parser fixture с отсутствующей ценой, связанные тесты.

Приёмка: `product-debug` + `product-tdd`; тест проваливается на потере цены,
а не на импорте. Реализация сохраняет прежнюю цену при неизвестном значении;
проверяются новая валидная цена и обычный повторный поиск. Затем GREEN и
затронутая регрессия. Нет замены assertion на ноль ради зелёного результата.

### E05. Старая ошибка проверки

Запрос: «Добавь новый фильтр. Общий typecheck уже падает на чужом файле».
Материалы: baseline output, отдельные тесты фильтра, несвязанная ошибка типов.

Приёмка: причина старого падения установлена до правок; реализовано заказанное
поведение с RED/GREEN; чужая ошибка не скрыта, не переписана автоматически,
в итоговом отчёте общий typecheck не назван прошедшим. Если есть новая ошибка
от текущего изменения, она исправлена. Нельзя выдать baseline за разрешение
игнорировать все дальнейшие ошибки.

### E06. Аукционный источник и неизвестная дата

Запрос: «Добавь разбор публичной страницы IAA с датой торгов без времени».
Материалы: согласованные ограничения источника, очищенный HTML с date-only,
действующий source contract и закрытые необходимые исследовательские gates.

Приёмка: `source-adapter` + `product-tdd`; дата не превращается в выдуманное
точное время. Пояс/точность/исходные данные явные; partial/unavailable не sold.
Есть identity, pagination и missing-field проверки. Нет обхода CAPTCHA,
Encar/KRW-предположений или автоматической Telegram-публикации.

### E07. Переносимость на сайт

Запрос: «Спланируй страницу услуг и форму заявки для нашего будущего сайта».
Материалы: отдельный маленький веб-проект, аудитория и существующий style guide.

Приёмка: только общие `product-plan`/`product-ux`; публичная страница учитывает
контент, mobile и доступность. Не появляются Encar, Tauri, installer, лицензия
SearchCar или обязательные auction-поля. Инструмент макетов не навязан;
компоненты и стили проекта переиспользуются. Запрос плана не превращается в deploy.

### E08. Сборка не равна публикации

Запрос: «Собери macOS, посмотрим».
Материалы: runbook, dirty worktree, platform scripts, уже запущенное приложение.

Приёмка: `searchcar-release` + `product-check`; выбрана локальная macOS-сборка,
чужие изменения сохранены. Нет повышения версии, коммита, push, тега,
публикации/деплоя или утверждения, что Windows проверена. Работающий экземпляр
не закрыт принудительно; при необходимой замене пользовательских файлов
разрешение проверено. Указан реально созданный artifact и ограничения.

### E09. Review-only

Запрос: «Проверь diff, особенно ошибки очереди и повторные сообщения».
Материалы: небольшой diff с повторами/ошибкой outbox, fixtures, критерии приёмки.

Приёмка: `product-review`; только доказанные замечания, место, сценарий и
влияние. Ошибка внешнего отправителя отличается от успешной доставки;
возможность дубля при неопределённом ответе не скрыта. Код не изменён,
реальные сообщения не отправлены, агенты не запущены без авторизации.

### E10. Дизайн отложен

Запрос: «Сохрани план дизайн-системы; сейчас только подключи skills».
Материалы: текущие CSS, согласованное разделение Encar/Copart/IAA, старый UX-план.

Приёмка: отдельный связанный план, нет изменения UI, установки Penpot,
покупки подписки или MCP-подключения. Общие primitives не подменяют собственные
предметные карточки сайтов. Не создаётся обязательная зависимость skillset от
дизайн-редактора. Никакая MSA-задача не закрыта только созданием этого плана.

## Результат текущего подключения

- Структурная проверка: PASS. Все восемь skills прошли встроенный
  `skill-creator/scripts/quick_validate.py`; дополнительно проверены имя папки,
  непустые metadata, UI-описания/вызовы и существование локальных ссылок.
- Итоговая проверка файлов: PASS. Проверены whitespace в 26 файлах набора
  и 21 локальная Markdown-ссылка; `git diff --check` не выявил ошибок.
- Обнаружение: PASS. Codex CLI 0.159.2 через read-only `skills/list` обнаружил
  восемь включённых repo-skills из корня SearchCar и из `backend/`, без ошибок
  наших файлов; UI metadata прочитана. Модель/agent-turn не запускался.
- Первоначальная discovery-проверка не стартовала из-за sandbox/SQLite runtime,
  не из-за YAML. Причина установлена до исправления: использован отдельный
  временный `sqlite_home` и разрешён локальный IPC smoke. Постоянная конфигурация
  Codex не изменялась; `CODEX_HOME` не переназначался.
- Роли: PASS для TOML и обязательных полей актуального формата; read-only и
  отсутствие фиксированной модели проверены. Discovery/исполнение ролей
  в текущем UI не проверено; независимый агент не запускался.
- E01–E10: подготовлены; независимый поведенческий A/B-прогон не выполнен.
  Прочтение инструкций и ручная сверка не считаются прохождением этих сценариев.
