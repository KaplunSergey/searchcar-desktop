# Как пишем и поддерживаем свои skills

Проверено 6 октября 2026 года. Это руководство для разработки набора, не skill,
который автоматически загружается при каждой продуктовой задаче.

## Актуальные источники и что используем

1. [OpenAI: Build skills](https://learn.chatgpt.com/docs/build-skills) —
   repo-discovery, явный/автоматический выбор, `SKILL.md`, UI metadata.
2. [OpenAI: Rethinking skills and prompts](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra),
   11 сентября 2026 — короткие точные descriptions, контекстные ссылки,
   отсутствие обязательного чтения всего проекта для маленькой правки.
3. Встроенный [OpenAI skill-creator](https://github.com/openai/skills/tree/main/skills/.system/skill-creator)
   — используем доступную в Codex версию для создания/обновления и валидации.
4. [Agent Skills specification](https://agentskills.io/specification) и
   [best practices](https://agentskills.io/skill-creation/best-practices) —
   формат, реальные проектные знания, контекст по необходимости, итерация
   по наблюдаемым ошибкам.
5. [Anthropic best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
   и [skill-creator](https://github.com/anthropics/skills/tree/main/skills/skill-creator)
   — полезные идеи eval-сценариев и сравнения с/без skill. Их runtime,
   Claude-specific команды и model settings не переносим в Codex автоматически.

Дополнительный creator поверх встроенного не установлен. ECC/SDD остаются
источниками идей, не двумя одновременно подключёнными workflow-системами.
Не обещаем, что сегодняшние инструкции вечны: формат/host проверяется
повторно при существенной правке или изменении клиента.

## Правила авторства

- Начинать с повторяющегося реального сценария/ошибки, не с общего учебника.
- Один skill — понятный результат; описание говорит когда его выбирать,
  а не пытается сработать на любое упоминание кода/дизайна/данных.
- `SKILL.md` содержит цель, существенные решения и границы. Большие условные
  процедуры — в references, с явным указанием когда читать.
- Не добавлять папки, assets и scripts без реального использования. Восемь
  текущих навыков короткие и не требуют искусственного reference-router.
- Общие skills не знают Tauri/Encar. Проектные — ссылаются на живые runbooks,
  а не хранят копии версий, команд и продуктового backlog.
- Требования безопасности/данных конкретны; открытые задачи оставляют свободу
  выбора. Нет обязательных моделей, тарифов, автокоммитов и нового чата на этап.
- Skill помогает выполнить запрос, не расширяет полномочия. Review/diagnosis
  не превращаются автоматически в fix, build — в publish.
- Текст пишем под собственные сценарии. При буквальном/существенном переносе
  upstream-текста сохранять его license/copyright и происхождение.

## Проверка перед подключением

1. Написать реалистичные запросы и критерии результата до длинных инструкций.
   Включить соседние задачи, где skill НЕ должен выбираться.
2. Проверить обязательные YAML-поля, имя папки, UI metadata и локальные ссылки.
   Использовать `quick_validate.py` доступного `skill-creator`; его успешный
   результат — проверка формата, не оценка поведения модели.
3. Проверить реальное обнаружение host. TOML-parser/schema для ролей не доказывает,
   что они появились в текущем чате или были корректно исполнены.
4. Для существенной/рискованной инструкции — независимый прогон сценариев
   в изолированном окружении при авторизованной делегации. Сравнить наблюдаемое
   поведение с/без skill, сохранив одинаковую модель и исходные материалы.
5. Исправлять только обнаруженную проблему, не добавлять универсальную
   инструкцию на каждое единичное исключение.

Ожидаемый RED теста продукта и ошибка доступа/импорта инструмента — разные
вещи. Для инструкций нельзя назвать regex-проверку слов полноценным TDD или
заявить эффективность набора без наблюдения поведения.
