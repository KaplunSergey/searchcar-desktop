# План дизайн-системы SearchCar

Дата: 6 октября 2026 года. Статус: сохранён для отдельного будущего этапа.
Сейчас не меняем UI, не устанавливаем инструменты и не реализуем компоненты.
Навигация по сайтам остаётся в [отдельном UX-плане](SOURCE_NAVIGATION_UX_PLAN.md),
порядок работы над функционалом — в [MSA-backlog](MULTISOURCE_IMPLEMENTATION_BACKLOG.md).

## Цель и границы

Единый визуальный язык: цвета, типографика, отступы, скругления, иконки,
состояния и анимации. Новые экраны используют готовые элементы, а изменение
общего элемента предсказуемо влияет на все его применения.

Не планируем полный редизайн, большой новый UI-framework или объединение
всех карточек. Encar, Copart и IAA сохраняют свои предметные композиции.
Общие primitives и стиль не означают одинаковое содержимое или смешанный UI.
Бизнес-логика парсеров/очереди не меняется ради оформления.

Начальная основа уже есть: CSS-переменные цветов и общие классы в
`app/globals.css`, компоненты/стили экранов в `app/page.tsx`, `app/details.css`
и desktop frontend. Это наблюдение по исходникам; визуальный baseline
нужно снять отдельно до выбора точных размеров и изменения стилей.

## Последовательные этапы после возврата к плану

### DS-01. Инвентаризация и baseline

Собрать существующие кнопки, поля, статусы, фильтры, панели, диалоги,
карточки/таблицы и повторяющиеся стили. Отметить настоящие дубли и оправданные
варианты. Снять ключевые экраны на поддерживаемых размерах окна и обеих ОС.

Результат: перечень элементов и расхождений, screenshots, согласованный
приоритет переноса. Не исправлять весь CSS одновременно.

### DS-02. Токены стиля

Зафиксировать семантические роли цветов: фон, поверхность, основной/вторичный
текст, граница, действие, успех, предупреждение, ошибка, фокус. Затем шкалы
типографики, отступов, скруглений, теней, размеров контролов и анимаций.

Точные значения выбираем по baseline, читаемости и текущему стилю, а не
копируем произвольную сетку из чужой библиотеки. CSS-токены в коде —
предлагаемый источник истины для приложения, подлежащий согласованию.

Приёмка: токены имеют понятное назначение; нужный цвет/отступ не приходится
изобретать заново; сохраняются контраст, focus и читаемость RU/UK.

### DS-03. Общие элементы и их состояния

Начать с Button/IconButton, полей ввода/select, Badge/Status, Panel,
заголовка с действиями, фильтров и диалога — только реально используемые
элементы. Интерактивные компоненты имеют disabled/loading/focus/error
состояния. Удобство клавиатуры и доступные подписи входят в контракт.

Общая кнопка не выполняет поиск и не знает об Encar. Общий статус оформляет
переданный смысл, но не вычисляет продано ли авто. Стили модулей локальны;
общие изменения проверяются на существующих потребителях.

Для поведения — тесты и проверенный RED/GREEN. Для визуальной миграции —
baseline и осмотр, не искусственный failing-test на буквальное значение CSS.

### DS-04. Живой каталог

Сделать локальную страницу-каталог элементов, вариантов и состояний с
теми же токенами/компонентами, что использует приложение. Она предназначена
для разработки и согласования, не обязана попасть в пользовательский bundle.

Начать с простой страницы; Storybook или visual-test runner добавлять лишь
при конкретной потребности. Сохранять понятные примеры допустимого применения.

Приёмка: можно открыть каталог и сравнить элементы без запуска поиска;
копии стилей каталога не расходятся с реальными элементами.

### DS-05. Постепенное применение

Переносить по одному семейству элементов/экрану, сохраняя функциональность,
фильтры, анимации сворачивания и пользовательские состояния. Сначала
существующий Encar, затем согласованная оболочка сайтов и новые auction UI.

EncarCard/EncarDetails, CopartLotCard/CopartLotDetails и IAA-композиции могут
оставаться отдельными. Общие аукционные блоки выделять из фактического
совпадения Copart/IAA, не заранее из предположения о похожести сайтов.

Приёмка каждого переноса: поведение сохранено, ненужный дубль удалён,
ключевые рендеры/взаимодействия проверены; нет скрытой регрессии другого модуля.

### DS-06. Поддержание системы

Для нового экрана сначала искать существующий компонент/вариант/токен.
Новый вариант добавлять, если старый не покрывает реальный сценарий;
отмечать его назначение в каталоге. Проверять новые состояния и consumers
общего изменения, а не только один экран.

Приёмка: правила можно выполнить и проверить, а не только прочитать;
будущий сайт переиспользует подход и подходящие элементы, но не обязан
копировать плотность/навигацию desktop-продукта.

## Инструменты макетов: решение отложено

React/HTML-прототип и каталог доступны без подписки на дизайн-сервис.
Penpot — опциональное место для редактируемых макетов, библиотек и обсуждения.
Если выбираем его, сначала проверить небольшой файл и MCP-интеграцию,
создание компонента, повторное применение и получение результата обратно.
Не обещать автоматическую синхронизацию с кодом: назначить направление
обновления токенов/компонентов и явно разрешать расхождения.

Excalidraw пригоден для черновых схем/сценариев; для дизайн-системы не обязателен.
OpenDesign и другие редакторы не являются зависимостью skillset.

Источники возможностей: [Penpot MCP](https://help.penpot.dev/mcp/),
[Excalidraw](https://github.com/excalidraw/excalidraw).

## Общая приёмка

- Один согласованный источник значений стиля и переиспользуемые элементы.
- Разные сайты сохраняют изолированные композиции и действия.
- Проверены RU/UK, длинные названия, узкое окно, клавиатура, loading/error,
  отсутствие фото/цены/даты и reduced motion для анимаций.
- Windows WebView2 и macOS WebKit проверяются отдельно; одинаковый браузерный
  screenshot не заменяет проверку обоих runtime.
- Новый компонент не нужен для каждой маленькой правки; переделка существующих
  экранов не считается автоматически согласованным редизайном.

Следующий шаг при возврате: согласовать DS-01 и baseline. Реализация этого
плана сейчас не начата; MSA-03 и другие продуктовые задачи им не закрываются.
