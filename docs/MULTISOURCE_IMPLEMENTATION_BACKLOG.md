## 1. Правила работы

- Закрываем задачи по порядку. Каждая следующая начинается после проверяемого
  результата предыдущей; внутри задачи сначала минимальный законченный сценарий.
- Статусы: `TODO`, `IN_PROGRESS`, `BLOCKED` с конкретной причиной, `DONE`.
  Создание документа/макета не означает, что функция работает в приложении.
- Одна задача — ограниченная правка и отчёт: сделано, проверки, ограничения,
  следующий шаг. Коммит/публикация/слияние — по отдельному запросу пользователя.
- Существующие незакоммиченные правки диагностики Windows не включаем в задачу
  автоматически, не откатываем и не маскируем ими результат новых проверок.
- Переиспользуем pytest, Node test runner, существующие fixtures, React/API и
  очередь. Новый тестовый фреймворк/универсальный конструктор UI не нужен заранее.
- Обе ОС обязательны. Прохождение тестов на macOS не считается доказательством
  работы Windows; результат платформенной проверки явно указывается.

### TDD: Red → Green → Refactor

Для задач с кодом:

1. Уточнить ожидаемое поведение и проверить ближайшие существующие тесты.
2. Добавить минимальную проверку нового правила/воспроизведение дефекта.
3. Запустить её и подтвердить **ожидаемую причину** падения. Ошибка импорта,
   отсутствующая сборка или неправильная тестовая БД не доказывают нужный Red.
4. Реализовать минимальное изменение; новый тест и затронутые старые — Green.
5. Рефакторить только на зелёных проверках; повторить регрессию и сборку по риску.

Выделение существующего Encar — characterization-тесты до переноса: фиксируем
правильное нынешнее поведение, переносим код, получаем тот же результат.
Не требуется искусственно ломать рабочую функцию ради красного теста.
Для исследований и дизайна вместо Red/Green — доказательства доступности,
согласованные правила/макеты и сценарии приёмки. Пустые тесты ради отчётности
не пишем. Сетевой smoke дополняет, но не заменяет детерминированные тесты.

### Если тест падает — сначала выясняем почему

1. Зафиксировать команду, среду, assertion/traceback и воспроизвести точечно.
2. Сравнить с baseline MSA-00; установить, появилось ли падение от текущей правки.
3. Классифицировать: новый дефект, старый дефект, устаревшая проверка устройства
   кода, окружение/сборка, недетерминированность, изменение реального источника.
4. Найти причину по потоку данных и вызывающим местам. Исправлять причину, а не
   менять ожидаемое значение, добавлять произвольный sleep или скрывать ошибку.
5. Менять тест допустимо, если согласованное требование изменилось или проверка
   привязана к старому расположению кода. Тогда сохраняем проверку поведения
   и объясняем изменение; просто удаление assertion/skip не является решением.
6. После исправления повторить исходный сценарий и связанные тесты. Неясное
   падение остаётся расследуемым/блокирующим, не объявляется «исправлено».

### MSA-02. Согласовать хранение и жизненный цикл лотов

**Подготовлено к решению 06.10.2026, статус остаётся TODO:** после проверки
списков предложен упрощённый первый сценарий — только выдача, краткий индекс
всех найденных лотов, «Сегодня» как локальная выборка, без автоматического
открытия карточек. Правила хранения уточнены ответами пользователя ниже. Выбор чтения
только списков не считается разрешённым каналом доступа и не закрывает MSA-01.

**Уточнения пользователя 06.10.2026:** без назначенной даты новые лоты пока
не добавлять; исчезнувшие убирать из активного списка после успешного полного
поиска по тем же условиям, без автоматического SOLD. Ошибка/отмена/ограниченный
охват не запускают исключение. Цена необязательна, ставка/Buy It Now/оценка
различаются. Нужен статус начавшегося аукциона: при сигнале сайта «Аукцион идёт»;
по одним часам предложено «Аукцион начался по расписанию», подпись не согласована.
Эти уточнения имеют приоритет над прежней рекомендацией хранения всех лотов ниже.

**Подтверждено следующим ответом «да, сохраняем»:** добавляем также будущие
датированные лоты; «Сегодня» — локальная выборка. Исчезнувшие исключаются из
активного списка с сохранением истории, без физического удаления всех данных.
История доставки и привязки к другим проектам не уничтожаются.

До изменения схемы/поведения нужно принять оставшиеся правила:

- Судьба уже сохранённого лота, у которого дата пропала; отображение избранного
  после исключения из активного списка. Отсутствие в выдаче при list-only
  не проверяется карточкой и не означает SOLD.
- Дата появилась — лот может добавиться; перенос меняет расписание, но сам по
  себе не доказывает новый раунд. Новые бездатные лоты в проект не добавляем.
- Время начала прошло — пометка, не подтверждённое завершение. В list-only
  автоматический архив допустим лишь при явном надёжном сигнале выдачи;
  иначе остаётся статус «результат не подтверждён».
- Неполный/ошибочный поиск сохраняет прежние данные и показывает их давность;
  предложение — не запускать первичную автоматическую доставку такого проекта.
- Автоматическое удаление метаданных/избранного/истории пока отложить.
- Формат Telegram без фото обсуждался как вариант, а не окончательная замена
  ранее согласованного фото; его нужно подтвердить отдельно до MSA-17.

После ответа синхронизировать условия MSA-09–14/17 с принятым вариантом,
не оставлять требования прямой перепроверки карточек в сценарии list-only.

**Результат:** пользователь выбирает объём хранения. Рекомендация пока не
утверждена: краткий индекс всей выдачи, подробности/фото преимущественно для
сегодняшних торгов; отсутствие в выдаче — проверка ссылки, не автоматическая
продажа; подтверждённое завершение — архив, повторные торги — новый раунд.
Определены поведение ограниченного охвата, избранного, снятия/отмены и
неполного поиска перед отправкой. Автоудаление архива предлагается отложить.

**Проверки:** сценарии «дата появилась», «перенос на завтра», «время прошло»,
«ошибка чтения», «повторные торги», «лот в двух проектах» согласованы.

**Закрытие:** нет неподтверждённого продуктового решения, от которого зависит
модель БД/архива. Технический вариант хранения не выбираем молча.

результатов/раундов, отмена, отчёт, планировщик, ресурсный лимит источника.
Все найденные записи обрабатываются по выбранной MSA-02 политике.

**TDD:** fake-adapter интеграция + реальные fixtures, выбранный охват/полнота,
частичный результат не sold, две подборки одного лота, повторный поиск,
ошибка подробностей без уничтожения данных, восстановление после перезапуска.

**Закрытие:** рабочий end-to-end Copart-поиск без Telegram, Encar независим.

### MSA-11. Реализовать карточку и страницу Copart

**Результат:** общая аукционная карточка IAA/Copart и отдельная страница Copart; дата/пояс,
повреждения/документы, ссылки, снимки данных, сортировка ближайших торгов.
UI получает нормализованные данные API, не сырой HTML источника.

**TDD:** отображение обязательных состояний даты, отсутствие цены/фото/поля,
безопасные ссылки/внешний текст, фильтры и пользовательские действия.
Визуальное сравнение с макетом и Encar дополнительно к автоматическим тестам.

**Закрытие:** экраны Copart работают на реальном поиске; композиция Encar не изменена.

### MSA-12. Реализовать чтение и поисковый процесс IAA

**Результат:** отдельный адаптер IAA, сохранение непрозрачной ссылки, нормализация
полей/дат, пагинация, worker/планировщик/отчёт. Контракт уточняется по реальным
различиям без Copart-условий внутри IAA и без второго общего worker.

**TDD:** fixtures IAA для поиска/лота/дат/ошибок; смена/недействительность ссылки,
дедупликация, полнота и повторный поиск; одинаковый ID с Copart/Encar не конфликтует.

**Закрытие:** реальный end-to-end IAA-поиск работает; регрессии обоих прежних
источников проходят. Если доступ изменился, сначала повтор MSA-01, не обход защиты.

### MSA-13. Реализовать UI IAA и выделить совпавшие аукционные блоки

**Результат:** подключение IAA к общей аукционной карточке, его страница и настройки; общие аукционные блоки
выделяются только из фактически совпавшего поведения двух работающих модулей.

**TDD:** те же общие правила даты плюс особенности IAA, переключение между
источниками, отличающиеся поля/единицы, длинные локализованные значения.

**Закрытие:** три сайта имеют собственные рабочие области, IAA/Copart — общую карточку, общий стиль
не смешивает данные и не навязывает Encar аукционные параметры.

### MSA-14. Завершить «Сегодня», обновление расписания и архив

**Результат:** вкладка «Сегодня» внутри Copart/IAA по проектам только этого сайта;
будущие/без даты/архив, проверка известных активных лотов и появившейся даты,
экономное чтение деталей по выбранной MSA-02 политике. Состав считается на
момент завершения поиска, а доставка позже повторно сверяет день/раунд.

**TDD:** перенос в/из сегодня, пропавший/бездатный известный лот, ограниченный
поиск, сон/полуночь, повторные торги, открытие страницы не запускает публикацию.

**Закрытие:** правильная локальная подборка и архив без автоматических ложных
продаж/удалений; поиск даёт стабильную основу для Telegram.

### MSA-15. Подключить Telegram безопасно

**Результат:** собственный бот/проверка соединения, права канала, chat ID;
секрет в отдельном Keychain/DPAPI-хранилище, канал/включение у проекта,
превью и явная тестовая отправка. Не используем формат ключа лицензии для токена.

**TDD:** корректный/неверный токен, права/приватный канал, URL проверен, токен
не попадает в API UI/логи/диагностику/backup, восстановление на другой машине
не запускает массовую доставку. API замокан; реальный тест только по явному действию.

**Закрытие:** подключение проверено на Windows/macOS, секрет не раскрывается.

### MSA-16. Реализовать устойчивую очередь доставки

**Результат:** задачи доставки после фиксации успешного поиска, состояния/журнал,
последовательная отправка, retry_after, отмена, восстановление после сна/запуска;
доставка не блокирует поисковый worker и не входит в транзакцию поиска.

**TDD:** 429/403/сеть, очередь после перезапуска, конкурентная постановка,
процесс прервался после отправки до сохранения message ID. Неопределённый
результат не повторяется вслепую, абсолютная exactly-once гарантия не обещается.

**Закрытие:** подтверждённые сообщения не дублируются, сбой доставки отдельно
от результата поиска; время контролируется тестом, не реальными sleep.

### MSA-17. Первичная публикация сегодняшних машин после поиска

**Результат:** фото + краткие сведения + локальная дата/время + ссылка; без фото
текстовый fallback. Только ещё не опубликованные лоты данного раунда/канала;
один лот в двух проектах одного канала — один пост. Время начала прошло —
публикация с пометкой, не отрицательным отсчётом. Учитывается выбранная MSA-02
политика неполного поиска; отправка выключена до явного включения.

**TDD:** поиск одного/нескольких проектов, повтор без изменений, два канала,
переименование проекта, начало прошло до/во время отправки, смена дня/статуса,
без даты/точного времени, экранирование текста/лимит сообщения, поздний результат.

**Закрытие:** ручной и запланированный поиск имеют одинаковые правила;
реальная публикация проверяется лишь в согласованный тестовый канал.

### MSA-18. Отдельные уведомления о переносах

**Результат:** после поиска подтверждённый перенос опубликованного лота создаёт
отдельное уведомление: прежняя/новая дата/время и ссылка. Исходный пост не
редактируется. Уведомление доходит и при переносе на завтра, только в каналы,
где первичная публикация этого раунда подтверждена. До первичной отправки
обновляется ожидающий пост, лишнего уведомления нет.

**TDD:** повторное чтение одной даты → без нового уведомления; A→B→C и A→B→A
→ разные события; смена пояса компьютера → не перенос; два проекта → один
пост об одном событии на канал; новый раунд отличается от переноса; сетевой retry.

**Закрытие:** каждый подтверждённый наблюдаемый перенос имеет одно событие
доставки на канал; полную карточку не публикуем заново ради новой даты.

### MSA-19. Общая приёмка, установленные сборки и подготовка выпуска

**Результат:** миграция очищенной старой копии данных, полный регрессионный набор,
реальный smoke трёх сайтов, UI RU/UK, сборки/обновление/повторный запуск обеих ОС.
Сохраняем наблюдаемые ограничения доступа и доставки, измеряем длительность
поиска/объём базы/медиа; оптимизацию без измерений не включаем в этот блок.

**Проверки:** все критичные сценарии MSA-04–18, license/source entitlement,
backup/перенос без секретов, изменения пояса/DST/сна, недоступность источника,
сохранность Encar и установленное приложение, не только dev-сервер.

**Закрытие:** обязательные проверки проходят на обеих ОС с доказательствами;
открытый дефект не скрыт названием «известная ошибка». Релизные заметки/список
изменений готовы. Коммит, push, merge и публикация — отдельные разрешённые шаги.

## 4. Как фиксировать закрытие задачи

При завершении рядом с заголовком указываем `DONE`, дату и краткое доказательство:
новый/characterization-тест, причина Red или расследованного падения, прошедшие
регрессионные команды, результат smoke/макета, ссылки на изменения и оставшиеся
ограничения. Если нужен Windows/реальный источник, но проверки нет, задача
не становится полностью закрытой лишь по локальному зелёному unit-тесту.

Следующий шаг после зафиксированного baseline — **MSA-01**.
Этот документ сам по себе не запускает следующие задачи.
Межсайтовые смешанные проекты/экраны, ставки/покупки, сервер доставки при
выключенном компьютере, универсальный переводчик, расширение пула workers и
автоматическое массовое удаление архива в этот блок не включены.
