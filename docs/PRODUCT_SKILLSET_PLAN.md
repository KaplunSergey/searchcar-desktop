# Собственный набор skills и инструментов для продукта

Дата исследования: 6 октября 2026 года.
Ветка SearchCar: `codex/multisource-auctions`.
Статус: собственный набор 1.0 создан в `.agents/skills`, роли ревью — в
`.codex/agents`. Новые внешние инструменты и полные ECC/SDD не устанавливались.
Фактические проверки и ограничения — в [PRODUCT_SKILLSET_EVALS.md](PRODUCT_SKILLSET_EVALS.md).

## 1. Решение

Собрать шесть общих skills для приложения и будущего сайта, плюс два навыка
SearchCar. Использовать идеи SDD для требований, UX и проверки результата,
ECC — для интеграций и специализированного ревью. Сохранить выбранный TDD
и правило: сначала выяснять причину падения тестов.

Общие skills содержат процесс и критерии решений. Особенности SearchCar
остаются в документации этого репозитория. Перенос общего набора в другой
проект не переносит Encar, Tauri, лицензионные правила или структуру базы.

Ponytail применяется к написанию, исправлению и рефакторингу кода.
Исследование, продуктовые требования, UX, визуальный дизайн и планирование
следуют задаче пользователя и своим критериям качества. Минимализм реализации
не сокращает согласованную функциональность, TDD, доступность, обработку
ошибок или проверку обеих ОС.

## 2. Что проверено в исходных проектах

### SDD

Изучен [genkovich/sdd](https://github.com/genkovich/sdd) версии 2.3.0,
commit `44039133714bea939e5cdfc86671a901b3b01ef0`.
Манифест заявляет 23 skills и 10 агентов.

Сильные стороны для нас:

- Требования связаны с наблюдаемыми критериями приёмки, задачами и проверками.
- `ux-flows` описывает путь пользователя, альтернативы и ошибки.
- `screens` описывает состояния экранов и используемые компоненты.
- `design-system` фиксирует источники токенов, компонентов и макетов.
- `plan-tests` связывает критерии с уровнями проверки.
- `fix` начинает с воспроизведения и локализации причины.
- TDD различает ожидаемый RED, ошибку самого теста/окружения и пропущенную
  проверку. Это совпадает с нашей потребностью расследовать падения.

Что адаптировать:

- Даже короткий маршрут требует spec → architecture → tasks → implement →
  review → ship. В матрице архитектуры остаются 12 секций Arc42; это избыточно
  для смены подписи, отступа или простого локального исправления.
- Частые подтверждения отдельных диаграмм, экранов и уровней тестов заменить
  вопросами только о действительно неясных продуктовых решениях.
- Обязательные промежуточные документы не должны блокировать работу, если
  нужные требования уже есть в существующем плане или сообщении пользователя.
- Убрать автокоммиты по умолчанию, принудительный новый чат между этапами,
  фиксированные модели и автоматическую оркестрацию.
- Первый зелёный тест не всегда слаб: characterization-тест перед переносом
  работающего Encar должен проходить. Это baseline, а не RED нового поведения.
- Интеграционная проверка SQLite может использовать временную реальную БД;
  обязательный Docker-контейнер из общего шаблона здесь не нужен.
- `design` в SDD означает техническую архитектуру. Продуктовый визуальный
  дизайн находится в `design-system`, `ux-flows`, `screens`.

Совместимость: SDD содержит installer для Codex, который создаёт skills
в `.agents/skills` и преобразует Markdown-агентов в `.codex/agents/*.toml`.
Его адаптер переводит Claude TeamCreate/Workflow в последовательное выполнение.
Это заявленная адаптация, а не результат проверки установленного SDD в нашем
Codex. Installer также меняет `.gitignore` и создаёт `.claude/sdd.local.md`;
его не запускали. Для собственного набора эти изменения не требуются.

Источники: [tool-adapters](https://github.com/genkovich/sdd/blob/44039133714bea939e5cdfc86671a901b3b01ef0/skills/_shared/tool-adapters.md),
[size-matrix](https://github.com/genkovich/sdd/blob/44039133714bea939e5cdfc86671a901b3b01ef0/skills/_shared/size-matrix.md),
[TDD loop](https://github.com/genkovich/sdd/blob/44039133714bea939e5cdfc86671a901b3b01ef0/skills/implement/references/tdd-loop.md),
[installer](https://github.com/genkovich/sdd/blob/44039133714bea939e5cdfc86671a901b3b01ef0/install.sh).

Берём идеи `api-connector-builder`, `frontend-design-direction`,

Нативный Codex-плагин ECC подключает skills, Chrome DevTools MCP и reviewed

с актуальным форматом, без копирования всей reference-конфигурации ECC.

Источники: [Codex plugin](https://github.com/affaan-m/ECC/tree/ef648e01899ba3e8dc6371642deaaf64b4477775/.codex-plugin),

## 3. Предлагаемый набор: шесть общих skills

| Имя | Когда используется | Результат | Основа |
| --- | --- | --- | --- |
| `product-plan` | Новая функция, крупное изменение, неоднозначные требования | Цель, границы, критерии приёмки, решения и последовательные задачи | SDD specify/clarify/roadmap/tasks; выборочные ADR |
| `product-ux` | Новые экраны, навигация, изменение сценария или визуального дизайна | Сценарии, состояния экранов, макеты, компоненты, критерии визуальной приёмки | SDD ux-flows/screens/design-system; ECC design-direction/a11y |
| `product-tdd` | Реализация нового поведения или изменение бизнес-правила | Проверенный RED, GREEN, затронутая регрессия и доказательства результата | SDD TDD; существующее правило SearchCar |
| `product-debug` | Диагностика ошибки или падение существующей проверки | Воспроизведение, baseline, причина, границы; исправление только если оно запрошено | SDD fix; ECC silent-failure-hunter |
| `product-review` | Ревью функции, diff или готовности | Доказанные замечания к требованиям, поведению, тестам и рискам | SDD review; ECC pr-test-analyzer/security-review |
| `product-check` | Проверка законченной правки перед передачей/коммитом/выпуском | Подходящие проверки, итог по каждому слою, явно непроверенные платформы | ECC verification-loop/browser-qa; проектные build/runbooks |

Границы:

- `product-plan` масштабируется: маленькая задача — краткое ожидаемое
  поведение; крупная — план в существующем документе либо отдельная спецификация.
- `product-ux` отвечает за сценарии и визуальные решения; архитектурные
  последствия отмечает в `product-plan`. Дизайн можно согласовать отдельно,
  как пользователь запросил для аукционных модулей.
- `product-debug` не превращает вопрос «почему?» в разрешение менять код.
- `product-review` сообщает замечания; не применяет исправления автоматически.
- `product-check` выбирает проверки по изменённым областям. Старое падение
  расследуется и отделяется от текущей правки; общая проверка не объявляется
  зелёной, если часть проверок не прошла или не запускалась.
- TDD применяется к поведению. Для исправления подписи/отступа достаточно
  осмотра; для переноса рабочего кода — characterization и регрессия.
- Коммит, push, PR, merge, публикация определяются запросом пользователя,
  а не названием skill или стадией процесса.

## 4. Два skill для SearchCar

| Имя | Задача | Особенности |
| --- | --- | --- |
| `source-adapter` | Подключить/изменить источник данных по принятому контракту | Проверить публичные данные; разделить transport, parsing, mapping; pagination, identity, price/currency, auction timezone, partial coverage; детерминированные fixtures и contract tests |
| `searchcar-release` | Подготовить сборку или выпуск SearchCar | Текущий RELEASE_RUNBOOK, версии UI/core/installer, updater, установленная версия и повторный запуск; независимые macOS/Windows доказательства |

`source-adapter` читает текущую архитектуру и согласованный backlog.
Отличия Encar и аукционов остаются в своих модулях; базовые компоненты
переиспользуются по смыслу. Он не начинает реализацию до закрытия исследований
доступности публичных данных, предусмотренных MSA-01.

`searchcar-release` читает реальные workflow и runbook при каждом выпуске.
Skill не хранит копию быстро устаревающих команд, ключей и номеров версий.
Запрос «собери macOS» не означает выпуск новой версии на GitHub.

## 5. Дизайн приложения и будущего сайта

`product-ux` имеет два режима на основе задачи:

- Продуктовый интерфейс: частые действия, плотность данных, навигация,
  списки, фильтры, карточки, детали, состояния и обратная связь.
- Публичный сайт: аудитория, цель страницы, содержание, визуальная иерархия,
  mobile layout, формы, accessibility и приёмка в браузере. Требования SEO
  и индексации добавляются для публичных страниц, а не автоматически для
  любого приложения.

Одна основа — токены, типографика, отступы, фокус, анимации и primitive-компоненты.
Состав карточки Encar и аукционного лота зависит от домена; стилистическое
сходство не требует объединять их в компонент с десятками условных полей.

Для SearchCar первой проверяемой дизайнерской задачей будет MSA-03:
выбор сайта слева → его проекты/запуски/настройки, плюс переключение сайтов,
сохранение контекста и состояния пусто/загрузка/ошибка. Отдельно — карточка
аукционного лота с местным временем, статусом даты, ссылкой и Telegram-состоянием.

Дизайн-система и инструменты вынесены в [DESIGN_SYSTEM_PLAN.md](DESIGN_SYSTEM_PLAN.md).
Реализация отложена по запросу пользователя. Основа плана — токены в коде,
переиспользуемые элементы и живой каталог. Penpot опционален, Excalidraw не
обязателен; skillset не зависит от OpenDesign/Figma/Pencil и платного сервиса.

## 6. Агенты: роли для выборочного ревью

При авторизованной делегации можно использовать доступный `explorer` для
исследования кода. Созданы три собственные read-only роли:

| Роль | Назначение | Граница |
| --- | --- | --- |
| `product-critic` | Неоднозначность требований, противоречия между планом и UX, неясные статусы/даты/повторные публикации | Читает материалы и даёт конкретные вопросы/замечания |
| `change-reviewer` | Требования, регрессии, качество тестов, проглоченные ошибки, безопасность изменённого пути | Review-only; каждое замечание подкреплено кодом и сценарием |
| `ux-reviewer` | Иерархия, состояния, accessibility, RU/UA-тексты, размеры окна, соответствие макету | Review-only; для визуальных выводов нужны реальные изображения/браузер |

Не требуем три агентных запуска для каждой правки. Независимое ревью
полезно для контракта источников, миграций, Telegram-дедупликации, updater и
крупной навигации. Запуск делегированной работы — по авторизации пользователя.
Роли наследуют выбранную модель; модели и бюджеты не копируются из Claude-шаблонов.

Codex поддерживает отдельные TOML-определения с `name`, `description`,
`developer_instructions` в `.codex/agents/`. Поэтому ECC-образцы без нового
формата не считаем готовой конфигурацией.
Источник: [официальные custom agents](https://learn.chatgpt.com/docs/agent-configuration/subagents).

## 7. Инструменты: что действительно нужно

| Инструмент | Сейчас | Роль |
| --- | --- | --- |
| Git, проектные scripts, Codex shell/diff | Есть | Изменения, состояние ветки, воспроизводимые команды |
| Web search и первичная документация | Есть | API, изменения сайтов, доступность публичных данных |
| pytest, Node test runner, TypeScript, ESLint | Объявлены в проекте | Детерминированные проверки, типы и lint |
| Playwright Python | Зависимость backend | Fixtures/live smoke парсеров; локальные браузерные сценарии при необходимости |
| Браузер/Computer Use | Доступен в сессии | Осмотр UI и реальные пользовательские действия |
| GitHub Actions, существующие platform build scripts | Есть в репозитории | Реальные сборки и проверки обеих ОС |
| OpenDesign | Skill доступен; runtime подключения не подтверждён | Макеты по отдельному brief и выбранному режиму |
| Playwright Test и visual baselines | Отдельный JS runner пока не объявлен | Добавлять для конкретных UI-регрессий; не выдавать Python Playwright за готовый visual test suite |
| Figma | Опционально | Внешний дизайн и совместная работа при появлении такой потребности |
| Cloudflare/Wrangler skills | Доступны; сервис лицензий использует Cloudflare | Deploy/диагностика текущего сервиса или будущего сайта на этой платформе |

В manifest уже есть commands и зависимости, но их наличие не доказывает
готовность runtime текущего shell. Перед запуском используется существующий
build runbook/runtime locator, а не новая глобальная установка по предположению.

Browser smoke не доказывает работу Tauri installer, sidecar, updater и shortcuts.
Они проверяются платформенными scripts/CI. Visual baselines сравниваются
в одинаковом окружении: рендеринг ОС и браузеров отличается.
Источники: [Tauri testing](https://v2.tauri.app/develop/tests/),
[Playwright visual comparisons](https://playwright.dev/docs/test-snapshots).

MCP добавляется, когда требуется реальный недоступный инструмент. Нет
основания подключать Memory, Sequential Thinking, Exa, Firecrawl, Chrome
DevTools и несколько браузерных MCP одновременно ради базового набора.

## 8. Принятый способ подключения и проверки

1. Создать общие `SKILL.md` в `.agents/skills/product-*` и проектные skills
   рядом. Пакет хранится в Git; системные и пользовательские плагины не изменяются.
2. Оставить в entrypoint цель, условия выбора и существенные правила.
   Развёрнутые режимы UX, диагностики и проверок — в references, читаемых по задаче.
   Никаких generic tutorials и hook-runtime без конкретной потребности.
3. Для SearchCar ссылаться на существующие планы, архитектуру и runbooks.
   Не переносить их содержание в общие skills и не создавать второй backlog.
4. Указать область Ponytail в проектных правилах: только код. Сначала
   проверить effective instructions, чтобы глобальный plugin не продолжал
   включать свой режим в исследовании/дизайне. Не редактировать plugin cache.
5. Добавить три role-файла в актуальном Codex-формате и проверить discovery
   через установленную версию Codex. Не менять глобальную модель/permissions.
6. Проверить frontmatter/ссылки и пять реалистичных сценариев: небольшая
   UI-правка; план новой функции без реализации; диагноз без разрешения на fix;
   дефект с ожидаемым RED; новый источник с неизвестной датой аукциона.
7. Дополнить проверкой двух продуктов: SearchCar и небольшой веб-прототип.
   Проверить, что общие skills не навязывают сайту Tauri и Encar, а desktop —
   обязательный SEO/мобильную структуру публичного сайта.
8. Исправить demonstrated conflicts, затем начать с первой согласованной
   задачи текущего backlog. Изменения правил и их подключение сами по себе
   не закрывают MSA-задачи продукта.

Для небольшого изменения достаточно поведения → правка → подходящая проверка.
Для бизнес-правила: критерии → RED → причина падения → GREEN → регрессия.
Для крупной функции: требования → UX при необходимости → границы/API/данные →
задачи и проверки → TDD → ревью → проверка работающего продукта.

Когда общий набор покажет пользу в обоих продуктах, выделить его в отдельный
Git-репозиторий или собственный Codex plugin. Версионирование позволит обновлять
проекты осознанно. Локальное хранение `.agents/skills` поддерживается Codex;
plugins предназначены для распространения набора между проектами.
Источник: [официальные skills](https://learn.chatgpt.com/docs/build-skills).

## 9. Происхождение и ограничения исследования

ECC и SDD имеют MIT LICENSE. При переносе текста или существенных частей
сохранить copyright и license notices в распространяемом наборе, а также
зафиксировать upstream commits. Новые инструкции пишем для своих сценариев;

## 10. Подключённый набор 1.0

Созданы восемь `SKILL.md` с UI metadata, три read-only role-файла, `AGENTS.md`
и явно читаемый `BOOST.md`. Общие skills не имеют зависимости от SearchCar,
