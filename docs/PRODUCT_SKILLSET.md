# Product skillset: как работаем

Версия набора: 1.0. Дата: 6 октября 2026 года.
Область: этот репозиторий; глобальные skills, модели, permissions и плагины
не изменены. Набор хранится в Git, но пока не закоммичен и не запушен.

## Состав

| Skill | Когда нужен | Результат |
| --- | --- | --- |
| `product-plan` | План функции/модуля, неоднозначные требования | Границы, критерии, решения и задачи |
| `product-ux` | Сценарии, новые экраны, визуальная система | Состояния, макет/прототип, правила переиспользования |
| `product-tdd` | Новое поведение, бизнес-правило или исправление | Проверенный RED, GREEN и затронутая регрессия |
| `product-debug` | Почему ошибка, падающий тест или runtime | Воспроизведение, baseline и доказанная причина |
| `product-review` | Проверка diff/готовой функции | Доказанные замечания без автоматической правки |
| `product-check` | Передача реализованной правки или сборки | Соразмерные проверки и честный статус |
| `source-adapter` | Сбор/разбор/нормализация источников SearchCar | Изолированный контракт сайта и его проверки |
| `searchcar-release` | Сборка, updater или разрешённый выпуск | Artifact/релиз и выполненные runbook-gates |

Первые шесть — общие для приложения и будущего сайта. Последние два знают
текущие планы/runbooks SearchCar и не переносятся в посторонний проект.
UI metadata каждого skill содержит русское название и пример запроса.

## Что происходит при обычном запросе

Codex видит короткие имена/описания, выбирает подходящий skill, читает его
инструкции и только нужные проектные материалы. Остальной набор не должен
загружаться целиком. Это выбор моделью, не жёсткая workflow-машина; точность
маршрутизации проверяется на реальных задачах и корректируется при ошибках.

Можно писать как обычно: «спланируй», «почему ошибка», «исправь», «собери».
Можно явно назвать нужный skill:

```text
Используй $product-plan: составь план функции, пока без кода.
Используй $product-debug: объясни падение поиска, пока не исправляй.
Используй $product-tdd: реализуй согласованное поведение.
Используй $product-review: проверь diff, не меняя его.
Используй $searchcar-release: собери macOS, без публикации.
```

Явное имя полезно, когда нужен определённый режим. Автоматическое обнаружение
включено по умолчанию; конфигурации explicit-only мы не добавляли. Если новый
skill не появился в списке текущего клиента, перезапустить Codex. Не считать
это гарантией выбора именно этим уже открытым чатом.
Источник: [официальное подключение skills](https://learn.chatgpt.com/docs/build-skills).

Фактический smoke: установленный Codex CLI 0.159.2 обнаружил все восемь
включённых repo-skills из корня и `backend/`, прочитал UI metadata без ошибок.
Это проверка загрузки, не доказательство точности автоматического выбора.

## Масштаб процесса

- Подпись/отступ: ожидаемый результат → маленькая правка → подходящая проверка.
- Бизнес-правило: критерий → baseline/RED → причина падения → GREEN → регрессия.
- Крупная функция: требования → UX при необходимости → границы/данные →
  последовательные задачи → TDD → ревью/проверка.
- Диагноз/ревью: исследовать и объяснить; не менять продукт без запроса.
- Локальная сборка: собрать и показать artifact; не выпускать версию автоматически.

Набор не заставляет писать шесть документов, запускать три модели или
переключаться в новый чат для каждой задачи. Вопросы задаются о важных
неясных решениях, не ради подтверждения каждой команды тестов.

Ponytail используется только для кода, рефакторинга и выбора зависимостей.
Он не уменьшает согласованный продукт, UX или набор существенных проверок.
Прямое изменение текста/CSS не требует искусственного RED; перенос рабочего
поведения может начинаться с зелёного characterization baseline.

## Роли ревью

В `.codex/agents/` подготовлены `product-critic`, `change-reviewer`, `ux-reviewer`.
Они имеют `sandbox_mode = "read-only"`, не фиксируют модель и не делегируют дальше.
Наличие TOML-файла не означает, что агент уже запущен или его поведение проверено.
Формат/required fields проверены; загрузка ролей текущим UI и независимый
поведенческий прогон пока не проверены.
Роли используются только по авторизованной делегации, не на каждой правке.

Например: «Подключи change-reviewer, пусть независимо проверит эту правку».
В передаче роли указываются задача, diff/base, материалы и запрет внешних
побочных действий. Итоговый ответ собирает основной агент после результата.
Если выбранный клиент не поддерживает/не обнаруживает custom roles, он
сообщает ограничение, а не выдаёт обычное собственное ревью за независимое.
Источник формата: [custom agents](https://learn.chatgpt.com/docs/agent-configuration/subagents).

## Где что хранится

- `AGENTS.md` явно направляет к `BOOST.md`, без зависимости от `@`-импортов.
- `BOOST.md` — короткие проектные границы и контекстные маршруты.
- `.agents/skills/<name>/SKILL.md` — сам skill;
  `agents/openai.yaml` рядом — отображение и пример вызова, не отдельный агент.
- `.codex/agents/*.toml` — отдельные роли ревью.
- [План/исследование набора](PRODUCT_SKILLSET_PLAN.md) — происхождение решений.
- [Авторство и актуальные источники](SKILL_AUTHORING_GUIDE.md) — как обновлять.
- [Сценарии проверки](PRODUCT_SKILLSET_EVALS.md) — критерии, evidence и ограничения.
- [План дизайн-системы](DESIGN_SYSTEM_PLAN.md) — отдельный отложенный этап.

Сейчас нет hooks, автокоммитов, обязательного MCP, Penpot/OpenDesign или
второй копии ECC/SDD. Продуктовый backlog не заменён набором skills.

## Перенос и сопровождение

Для другого продукта переносить шесть папок `product-*` целиком вместе с
UI metadata. Не переносить проектные skills и `BOOST.md` SearchCar. Сначала
сверить существующие имена/навыки в целевом проекте: дубли по имени Codex
не объединяет. Сделать один проверяемый перенос, не одновременно глобальную
и repo-копию одних skills.

После реальной ошибки выбора/решения уточнить description или конкретный
раздел skill; не наращивать общие запреты и не обновлять upstream автоматически.
При правке существенного поведения skill использовать встроенный `skill-creator`,
проверку формата, discovery и подходящие сценарии. Источник версий приложения —
его runbook, а не этот документ.

Если набор подтвердит пользу в двух продуктах, отдельно обсудить собственный
repo/plugin и версионированные обновления. Сейчас нового publish/install runtime
для распространения не требуется.
