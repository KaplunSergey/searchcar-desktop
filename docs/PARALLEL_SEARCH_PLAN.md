# Параллельный поиск SearchCar Desktop

Дата: 8 сентября 2026 года. Статус: предложение для обсуждения, реализация не начата.

Две отдельные задачи: **PAR-1 — параллельные проекты** и **PAR-2 — параллельное
чтение машин внутри проекта**. Рекомендуемый порядок: общая подготовка → PAR-2 →
сравнение результатов → PAR-1. Настройки производительности общие для обеих задач.
До реализации каждой задачи согласуются сценарий и критерии приёмки.

## 1. Что делает текущая версия

Проверено по локальному коду, а не по предположению о количестве потоков:

| Участок | Текущее поведение | Где смотреть |
| --- | --- | --- |
| Desktop runtime | Один фоновый поток поиска; отдельный поток синхронизации лицензии | `backend/app/desktop_runtime.py`, `main` |
| Очередь | Только один активный `ScanRun`; следующий запуск ждёт | `backend/app/job_queue.py`, `claim_next_job`; `backend/app/sqlite_migrations.py`, `uq_scan_runs_single_active_worker` |
| Проекты | Последовательный цикл в одном запуске | `backend/app/worker.py`, `process_job` |
| Браузер | Sync Playwright, один браузер, контекст и страница | `backend/app/worker.py`, `process_job` |
| Выдача и карточки | Сначала последовательный обход страниц проекта, затем машин | `backend/app/scanner.py`, `collect_search_pages`, `read_detail` |
| Цена | Изменившаяся цена требует повторного чтения подробностей | `backend/app/worker.py`, `_read_verified_detail` |
| Сохранение | Чтение карточки сразу пишет изображения; worker обновляет БД и отчёт | `backend/app/scanner.py`, `_replace_file`; `backend/app/services.py`, `upsert_detail` |
| Прогресс | Один `current_project_id`, общие списки отчёта и ошибок | `backend/app/worker.py`; `app/page.tsx` |

Время расходуется не только на Python: переходы страниц, ожидания содержимого,
прокрутка, повторные чтения, скриншоты и загрузка фотографий тоже входят в поиск.
Параллельность совмещает часть этих ожиданий, но сама по себе не уменьшает число
нужных запросов и не исправляет неполные страницы.

## 2. Сравнение двух задач

| Критерий | PAR-1: несколько проектов | PAR-2: несколько машин одного проекта |
| --- | --- | --- |
| Единица работы | Шаги нескольких проектов чередуются и выполняются одновременно | Подробные карточки одного проекта читаются одновременно |
| Первый вариант | До двух проектов, в каждом не больше одной активной браузерной операции | Один проект, до двух одновременно обрабатываемых машин |
| Один большой проект | Практически не ускоряет | Основной полезный сценарий |
| Несколько сопоставимых проектов | Хорошо распределяет работу | Каждый проект заканчивается быстрее, следующий начинается после него |
| Много быстрых проверок без изменений | Может совместить обход выдачи разных проектов | Эффект небольшой, если карточки не требуется открывать |
| Очень разные размеры проектов | После малого проекта один исполнитель может остаться без работы | Два исполнителя продолжают разбирать большой проект |
| Прогресс и отмена | Нужны независимые состояния нескольких активных проектов | Сохраняется один активный проект, добавляются счётчики карточек |
| Пересечения машин | Главный риск: одна машина в нескольких проектах | Нужна дедупликация внутри проекта и при редиректах |
| Сложность в текущем коде | 5/5 | 4/5 |
| Предлагаемая важность | 7/10, выше при множестве быстрых проектов | 8/10, особенно для первого точного поиска |

Это оценки устройства реализации, а не результаты замеров. При одинаковом числе
браузерных исполнителей нагрузка может быть сопоставимой: два проекта не
обязательно тяжелее двух подробных страниц. Определяет нагрузку фактически
открытый контент, количество браузеров, изображений и одновременно выполняемых
операций.

### Ожидаемая скорость: расчёт, а не обещание

Для карточек приближённая модель времени: `T(N) = S + D/N + O(N)`, где `S` —
последовательная часть, `D` — распараллеливаемая, `O` — дополнительные затраты.
Ограничение частоты запросов сайта может дополнительно ограничить ускорение.

- Если подробности занимают 80% времени, два исполнителя дают теоретически
  около 1,67×, то есть на 40% меньше времени, без учёта дополнительных затрат.
- Если подробности занимают 20%, предел в той же модели — около 1,11×.
- Для проектов по 100 и 10 машин при условных 5 секундах на машину: последовательно
  550 секунд; два проекта параллельно — 500; две машины внутри проекта — 275.
  Здесь намеренно не учтены выдача, лимиты сайта, повторы и сохранение.
- Для двух одинаковых проектов идеальное ускорение PAR-1 приближается к 2×,
  но на реальном компьютере и сайте может оказаться существенно меньше.

Нужно измерять не только общий финал: время до первой сохранённой машины,
первого завершённого проекта и появления важного изменения тоже влияет на UX.

## 3. Общая архитектура

Сохранить **один активный ScanRun и один управляющий worker**. Его внутренние
исполнители работают параллельно. Это позволяет оставить защиту очереди и
уникальный индекс одного активного запуска, существующую историю и расписание.
Запускать несколько `process_job` и снимать ограничение БД для этих задач не нужно.

Поток данных:

`координатор → ограниченная очередь задач → браузерные исполнители → ограниченная
очередь результатов → координатор → файлы/БД/события/прогресс`.

### Исполнители

Для первого внедрения предпочтителен небольшой пул постоянных потоков с
текущим sync Playwright. Каждый поток самостоятельно создаёт, использует и
закрывает собственные Playwright, браузер, контекст и страницу. Один экземпляр
живёт на серию задач, а не запускается заново для каждой машины. Нельзя передавать
`page`, контекст или Playwright из основного потока в другие потоки: API не
потокобезопасен. [Документация Playwright](https://playwright.dev/python/docs/library#threading)

Начальная реализация: `threading`, `queue.Queue`, `Event` из стандартной
библиотеки. Размер очередей ограничен, например несколькими задачами на
исполнителя; фотографии передаются как пути к временным файлам, а не как
неограниченные массивы байтов. Исполнители не ждут друг друга и не создают
вложенных пулов. Небольшое опережающее заполнение очереди сохраняет возможность
остановки и изменения приоритетов.

**Все браузеры учитываются в общем лимите**, включая чтение выдачи. Нельзя
незаметно оставить браузер координатора и добавить к нему ещё два. В пилоте
достаточно максимум двух исполнителей на приложение; контексты между задачами
переиспользуются по правилам источника, без смены идентичности ради блокировок.

Альтернатива — async Playwright и несколько страниц одного браузера. Это может
уменьшить накладные расходы браузеров, но требует перевода вызовов scanner,
ожиданий, callback и отмены на async. Parser и запись БД не обязаны становиться
async. Сначала сравнить два прототипа на локальных страницах; переходить на async,
если память sync-варианта не укладывается в бюджет. Не поддерживать два полноценных
движка постоянно. Пул отдельных Python-процессов пока не оправдан: добавляет
сложности Nuitka onefile, обмена результатами и завершения на Windows.

### Запись и согласованность

- Только координатор записывает результаты поиска в БД, изменяет `ScanRun`,
  `ProjectScanRun`, отчёт, историю и события. API приложения по-прежнему может
  записывать пользовательские изменения: нужны короткие транзакции и повторная
  проверка актуального состояния при применении результата.
- В браузерные потоки идут простые копии данных: источник, URL, ID проекта,
  исходная цена, версия наблюдения, идентификатор задачи. ORM-объекты и общая
  `Session` между потоками не передаются. SQLAlchemy требует отдельного владельца
  сессии для каждой параллельной работы. [SQLAlchemy](https://docs.sqlalchemy.org/en/20/orm/session_basics.html#is-the-session-thread-safe-is-asyncsession-safe-to-share-in-concurrent-tasks)
- WAL позволяет читать базу во время записи, но не делает записи нескольких
  потоков одновременно независимыми. [SQLite WAL](https://sqlite.org/wal.html#concurrency)
- Одна пара `(источник, ID объявления)` имеет только одно незавершённое чтение.
  Повторный запрос присоединяется к результату; после получения canonical ID
  координатор дополнительно разрешает коллизии. Дедупликация живёт в пределах
  запуска и учитывает проверенную идентичность, без вечного кэша свежести.
- Факты автомобиля и наблюдение проекта разделяются: общий снимок может быть
  один, но присутствие в выдаче, предыдущая цена наблюдения и отчёт различаются
  по проектам. Подключение второго проекта не должно дублировать общее событие
  цены или уведомление, но должно сохранить его собственное наблюдение.
- Каждый task пишет изображения в уникальную временную директорию. Только
  принятый результат публикуется в основное хранилище. Нынешнее общее имя `.tmp`
  нельзя использовать при конкуренции. Для согласованности файлов и БД предусмотреть
  уникальные версии файлов: сначала готовый файл, затем транзакция со ссылкой и
  checksum; удаление старой версии только после отсутствия ссылок на неё.
  При сбое может остаться невостребованный файл, но не ссылка на полузаписанный.
- Повторная проверка изменившейся цены остаётся частью одной задачи. Результат
  получает время наблюдения и исходную версию; запоздавшая задача не откатывает
  более свежие данные. При конфликте не создаётся ценовое событие без проверки.
- Перед сохранением повторно проверяются удаление проекта, исключение машины,
  отключение отслеживания и действующие ограничения лицензии. Событие становится
  доступным для уведомления только после commit. Проверка разрешения источника
  использует существующее состояние лицензии и сигнал его изменения; отдельный
  удалённый запрос лицензирования на каждую машину не добавляется.

## 4. Ограничения источника, ошибки и CAPTCHA

Увеличение параллельности может повысить вероятность ограничений. Ни пул, ни
паузы не гарантируют отсутствия CAPTCHA. Цель — меньше лишних запросов и
корректная реакция на ограничения; маскировка автоматизации, смена IP/отпечатков
и обход CAPTCHA не входят в реализацию.

Два независимых ограничения: число одновременно выполняемых операций и частота
их начала. Мощность компьютера не разрешает увеличивать нагрузку на источник
выше его лимита. Точное разрешённое значение для Encar сейчас не установлено;
пилотный лимит 2 — технический верхний предел приложения, а не заявление о
допустимой частоте сайта. Стартовать с 1 и повышать только после проверки условий
доступа и аккуратного замера, без нагрузочного теста чужого сайта.

Необходимые правила:

1. Один общий ограничитель для всех проектов данного источника, чтения карточек,
   подтверждения цены, повторов и явной загрузки изображений. Навигация страницы
   порождает дополнительные HTTP-запросы; два слота не означают два запроса.
   Собирать количество и объём сетевых обращений, не ломая необходимые ресурсы.
2. Сохранять текущие проверки свежести, не читать одну карточку повторно ради
   каждого пересекающегося проекта. Не убирать обязательное подтверждение цены
   и не ограничивать страницы ради красивого результата замера.
3. При `429` соблюдать `Retry-After`, если он есть; при временных сбоях использовать
   ограниченные повторы с увеличением пауз. Навигация должна проверять HTTP-ответ,
   которого сейчас `_open_page` не анализирует. [RFC 6585](https://www.rfc-editor.org/rfc/rfc6585#section-4)
4. При CAPTCHA или явном запрете доступа прекращать выдачу новых задач источника,
   сохранять уже подтверждённые результаты и понятную причину остановки. Не
   повторять запросы автоматически в бесконечном цикле. `403` классифицировать,
   а не считать автоматически временным таймаутом.
5. Проверить HTML и содержимое страницы: блокировка может прийти и с HTTP 200.
   Неполную страницу не считать автоматически CAPTCHA или продажей.
6. Для временной паузы сохранять `retry_not_before` источника: ручной запуск,
   планировщик и перезапуск приложения не должны сбрасывать ожидание. Длительное
   ожидание не удерживает зря браузеры; интерфейс показывает причину и следующий
   допустимый момент. CAPTCHA требует явного действия пользователя после
   устранения причины, а не запуска таймера повторов.
7. В будущем разные источники имеют отдельные лимиты и причины остановки; ошибка
   Encar не обязана останавливать другой разрешённый источник. Существующие
   правила отзыва лицензии остаются обязательными.

**Найденный дефект, который исправляется до пула:** ошибки `ScanError` на карточке
в `worker.py` ловятся с продолжением цикла; в ветках пропавших и вручную выбранных
машин также есть широкие обработчики. `stop_for_captcha` устанавливается во
внешнем обработчике проекта, поэтому CAPTCHA на карточках не останавливает поиск
единообразно. Нужен общий сигнал остановки источника во всех этих путях.

## 5. Режимы производительности и подбор под компьютер

Настройка: **Настройки → Поиск → Нагрузка на компьютер**. Она не смешивается с
`Быстрый / Точный`: точность определяет состав проверки, производительность —
количество одновременных операций. Первый поиск остаётся точным по всем страницам
при любом режиме производительности.

| Режим | Предлагаемое поведение пилота | Текст для пользователя |
| --- | --- | --- |
| Экономный | 1 исполнитель, увеличенная пауза между заданиями; освобождать ненужный браузер | Поиск займёт больше времени, компьютер будет меньше нагружен |
| Автоматический | Начать с 1, разрешать до 2 при достаточных ресурсах и лимите сайта | Приложение подбирает нагрузку под ваш компьютер |
| Ускоренный | До 2 при наличии работы; защитное снижение при нехватке ресурсов сохраняется | Проверяет несколько страниц одновременно; может сильнее нагружать компьютер |

После проверки авто-режима он может стать значением по умолчанию. До этого у
существующих установок остаётся 1 исполнитель. `До 2` не гарантирует два слота:
сайт может требовать паузу или в очереди может быть только одна задача.

Число ядер само по себе недостаточно. Учитываются доступная память, текущая
загрузка CPU, питание от батареи, запас памяти на дерево Chromium/драйвера,
задержки сохранения, ошибки сайта и прирост полезной скорости.

Фактический параллелизм:

`min(лимит режима, бюджет компьютера, лимит источника, готовые независимые задачи)`.

Предлагаемый простой регулятор:

- первая серия задач идёт с одним исполнителем; измеряется потребление;
- второй включается лишь после устойчивого запаса ресурсов; память проверяется
  по `available`, а не только по общему объёму или показателю `free`;
- ориентиры для пилота: резерв памяти не меньше `max(2 GiB, 20% RAM)`, повышать
  при CPU ниже 60% и стабильном состоянии около минуты; снижать после устойчивых
  значений выше 85% или уменьшения запаса памяти. Эти числа — стартовые гипотезы,
  их нужно настроить по замерам Windows/macOS, а не объявлять универсальными;
- повышение только на один слот; между изменениями пауза; снижение прекращает
  новые выдачи, а не обрывает корректную запись; ненужный браузер затем закрывается;
- в авто-режиме на батарее предпочитать 1; ручной выбор ускоренного режима
  сохраняется, но не отключает защиту от нехватки ресурсов;
- если метрики недоступны, работать с 1. Не требовать датчика температуры:
  доступность таких датчиков различается между устройствами;
- при тяжёлом давлении памяти возможна пауза выдачи и освобождение браузера даже
  при одном исполнителе. Режим не может гарантировать отсутствие нагрузки;
- изменение режима во время поиска применяется на безопасной границе задачи;
  пользователю показывается выбранный режим, реальный лимит и причина снижения.

Для измерений сначала проверить доступные средства runtime. В текущих зависимостях
нет `psutil`/`sysinfo`; если понадобится единый кроссплатформенный слой CPU/RAM/
батареи, практичен бесплатный `psutil`. Это отдельная зависимость, требующая
проверки упаковки Nuitka на обеих ОС; версию выбирать и фиксировать при реализации.
Метрики CPU, доступной памяти и батареи документированы в
[psutil](https://psutil.readthedocs.io/stable/index.html). Наблюдение за нагрузкой
локальное, без сервера аналитики. Память дерева процессов оценивается приближённо,
основной ограничитель — доступная системная память.

## 6. PAR-2 — параллельные машины: этапы

1. Отделить браузерное чтение от применения результата в worker, сохранив
   последовательное поведение при лимите 1. Выдача проекта пока остаётся
   последовательной, со всеми нынешними проверками пагинации.
2. Формировать задачи только для машин, которым реально нужно чтение; сохранить
   проверки новых/неполных/изменённых машин, ветки пропавших и ручного обновления.
   Передавать исходную цену и версию обычными значениями вместо `Car` из ORM.
3. Добавить двух исполнителей на общем бюджете. Каждая задача целиком включает
   проверку идентичности, нужное подтверждение цены и сбор изображений.
4. Принимать результат по готовности: медленная первая машина не удерживает
   результаты остальных. Координатор сохраняет актуальные данные и делает
   доступными события, затем обновляет прогресс.
5. Показывать `Сохранено 37 из 120 · Проверяются 2`, отдельно ошибки и пропуски.
   Пока полный объём не известен, показывать этап и счётчики без ложного ETA.
6. Завершать проект только после обработки всех задач, требуемых дополнительных
   проверок и записи итогов. Отсутствие в выдаче рассчитывать только при
   подтверждённо полном сборе выдачи, не по порядку завершения карточек.
7. Подключить режимы нагрузки, проверить экономный и ускоренный варианты,
   затем включать автоматический регулятор.

Готовность: один большой точный проект ускоряется в воспроизводимом сценарии;
результаты, подтверждение цен, история, ошибки и ссылки совпадают по смыслу с
режимом 1; можно остановить поиск без потери уже сохранённых данных.

## 7. PAR-1 — параллельные проекты: этапы

1. Вынести изменяемое состояние каждого проекта из общего цикла: этап, исходные
   наблюдения, выдача, найденные/проверенные ID, оставшиеся задачи, ошибки,
   завершённость страниц. Общие счётчики меняет только координатор.
2. В первом эксперименте обрабатывать два проекта, но не больше одной
   браузерной задачи на проект одновременно; общий пул остаётся максимум 2.
   Следующий проект занимает место закончившегося. Сравнивать с PAR-2 при том же
   числе слотов и лимите источника.
3. Переиспользовать чтение общей машины в пределах запуска. Для каждого проекта
   отдельно сохранять факт обнаружения, статус и отчёт относительно его прежнего
   наблюдения; не переносить наличие машины из выдачи одного проекта в другой.
4. Добавить список активных проектов и их независимый прогресс. Сохранить чтение
   старых отчётов с `current_project_id`; не менять исторические данные ради UI.
   Число завершённых проектов считать по конечным статусам: сейчас UI считает
   все ключи `project_statuses`, и добавление туда `RUNNING` исказило бы счётчик.
5. Обновить удаление активного проекта, отмену, sleep, recovery и итоговую
   агрегацию. Завершение малого проекта не завершает весь `ScanRun`.
6. Разрешать `mark_absent` для проекта только после полного его обхода и
   обработки необходимых результатов; сбой другого проекта не делает эту
   выдачу неполной. Незавершённый проект не помечает машины отсутствующими.
7. Планировщик учитывает итог всего запуска, не стартует дубликат при работающих
   дочерних задачах. Проверить нынешнюю привязку интервала к завершению и catch-up.
8. После отдельного сравнения можно объединить стратегии: один общий пул выдаёт
   слоты карточкам и страницам разных проектов справедливо, не оставляя малый
   проект ждать бесконечно. Никакого умножения `2 проекта × 2 машины = 4` без
   отдельного увеличения общего лимита и повторной проверки.

Готовность: прогресс нескольких проектов правдивый; пересекающиеся машины не
создают гонки файлов/БД/событий; отмена и удаление не сохраняют запоздалые данные;
набор итогов не зависит от того, какой проект завершился первым.

## 8. Остановка, сон, обновление и восстановление

Установка флага отмены не прерывает уже выполняющийся синхронный вызов браузера.
Даже `Future.cancel` отменяет только ещё не начатую работу.
[Python concurrent.futures](https://docs.python.org/3.12/library/concurrent.futures.html#concurrent.futures.Executor.shutdown)

Сейчас runtime ждёт worker 35 секунд, тогда как отдельная навигация допускает
60 секунд и повторы. Перед пулом нужно согласовать общий срок остановки с
таймаутами браузерных операций, добавить проверки отмены внутри чтения,
прокрутки, повторов и скачивания. Нельзя просто умножить ожидание на число потоков.

Порядок остановки: прекратить выдачу → отменить очередь → завершить/отклонить
результаты активных задач по одной согласованной границе отмены → закрыть браузеры
в их потоках → записать итоговый частичный отчёт. После конечного статуса поздние
результаты не применяются. Идентификатор запуска и поколения задачи защищает от
результатов, пришедших после перезапуска или восстановления.

Проверить зависший браузер и очистку только принадлежащих приложению дочерних
процессов через существующий runtime. Поток Python нельзя надёжно принудительно
остановить: если согласованный срок не обеспечивается выбранной моделью,
пересмотреть границу изоляции до выпуска. Не освобождать очередь и не начинать
restore/update, пока старые исполнители могут писать файлы. Фоновый режим и сон
должны сохранять текущую семантику частичного отчёта; параллельность не отменяет сон.

Backup должен видеть согласованный набор БД и изображений. Сохранить существующий
maintenance lock и запрет экспорта при активном поиске (`desktop_backup.py`,
`export_backup`). Активный запуск не заканчивается раньше очистки исполнителей.
Restore/update также требуют полной остановки. Backup одновременно с поиском
не входит в эти задачи. Проверить совместимость с автоматическими backup,
переносом данных и устаревшими записями активных запусков.

## 9. Как объективно сравнивать

Сначала локальные воспроизводимые страницы и существующие Encar fixtures;
управляемо задавать время выдачи, карточки, фотографий, таймауты, CAPTCHA и 429.
Не гонять нагрузочные тесты на живом Encar. Затем небольшой реальный smoke-тест
обычной пользовательской выборки при допустимом доступе.

| Сценарий | Что сравниваем |
| --- | --- |
| Один точный проект, 100 карточек | PAR-2 против текущего режима |
| Два проекта по 50 карточек | PAR-1 против PAR-2 при общем лимите 2 |
| Проекты на 100 и 10 карточек | Дисбаланс, время первого результата и общего завершения |
| Несколько быстрых проектов без изменений | Эффект параллельного обхода выдачи |
| Половина машин общая для проектов | Дедупликация, запросы, история и проектные наблюдения |
| Изменённая цена, неполная карточка, медленная фотография | Подтверждение, очереди, сохранение скорости и качества |
| CAPTCHA/429 в выдаче, карточке, пропавшей и ручной машине | Единая остановка/пауза источника и отсутствие новых запросов |
| Сон/выход/отмена/удаление/отзыв доступа/restore | Корректная граница остановки и отсутствие поздних записей |

Сравнивать с одинаковой копией БД, одинаковыми режимами точности, страницами,
лимитом источника и набором входных данных. Разделять холодный и прогретый
браузер; иначе повторный поиск новых машин окажется быстрым из-за старой базы.
На локальном стенде минимум три повтора, сравнение медианы; для p95 длительности
карточек собирать достаточно отдельных наблюдений. Проверить Windows x64 и
macOS Apple Silicon, слабый ноутбук/сильный компьютер, батарею/сеть питания.

Метрики: общее время, карточки с корректно сохранёнными результатами в минуту,
время первого изменения, этапы выдачи/подробностей/изображений/БД, CPU, доступная
RAM, приближённая память дерева браузера, задержки UI, сетевые обращения/байты,
очередь сохранения, повторы, неполные страницы, ограничения и время остановки.
Записывать режим и причину изменения слотов в существующие диагностические
журналы; включать их в отчёт за последний час. Секреты и полные страницы не логировать.

Предварительный критерий пользы: не менее 20% сокращения времени на целевом
локальном сценарии с двумя слотами, без ухудшения данных, отзывчивости и
остановки. Это порог решения о внедрении, не прогноз для всех компьютеров.
Рост ошибок или отсутствие выигрыша означает снижение лимита/пересмотр подхода.
Малый smoke-тест не доказывает, что CAPTCHA никогда не появится.

## 10. Последовательность работ и объём

| Этап | Результат | Сложность |
| --- | --- | --- |
| Общий A | Замеры текущей версии, сравнение sync/async прототипов на локальном стенде | 2/5 |
| Общий B | Единая обработка CAPTCHA/429/отмены, сроки остановки и восстановление | 4/5 |
| Общий C | Разделение чтения/записи, уникальные файлы, ограниченные очереди, лимиты источника | 4/5 |
| PAR-2 | Две машины внутри проекта, счётчики, ручные режимы нагрузки | 4/5 |
| Общий D | Динамический режим Auto, метрики устройства и диагностика | 3/5 |
| PAR-1 | Независимые проекты, общие машины, прогресс, удаление и планировщик | 5/5 |
| Завершение | Сравнение при одинаковом бюджете, packaged smoke обеих ОС, выбранные дефолты | 3/5 |

Точные сроки определяются после Общего A и решения о модели браузера. Это
изменение ядра поиска с несколькими проверяемыми этапами, а не добавление одного
`ThreadPoolExecutor`. Общую подготовку реализовать один раз для обеих задач.
Полный переход на адаптеры всех источников не блокирует PAR-2: достаточно
явного ключа источника и границы браузерного чтения; связать их с текущей задачей
17, не создавать второй конкурирующий механизм выбора источника.

Изменения затронут `worker.py`, `scanner.py`, `services.py`, `job_queue.py`,
desktop runtime, хранение настроек и схемы API, `app/page.tsx`, переводы,
диагностику и тесты. Нужность миграции настроек/состояния паузы определить по
существующему хранилищу при реализации. Общую историю старых запусков сохранить.

Проверки добавляются к существующим тестам worker, scanner, очереди,
целостности карточек и desktop runtime плюс локальные интеграционные сценарии
конкуренции. CI и сборки остаются ручными; большие браузерные кэши, внешняя очередь,
облачные вычисления, proxy и платная аналитика не требуются.

Перед включением пользователям должны пройти: одинаковый результат при 1/2,
отсутствие дубликатов, корректная остановка и очистка процессов, рабочий backup,
история после перезапуска и реальный тест упакованных macOS/Windows приложений.
Любой режим всегда допускает возврат к одному исполнителю через настройки.
