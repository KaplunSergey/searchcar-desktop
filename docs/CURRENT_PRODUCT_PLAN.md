# Текущий продуктовый план SearchCar Desktop

Дата актуализации: 21 сентября 2026 года.

Этот документ содержит согласованный список улучшений, которые планируется
реализовать в текущем цикле развития. Номера задач сохранены из первоначального
обзора рынка, поэтому они не идут подряд.

Технический план превращения web-приложения в desktop по-прежнему находится в
[`DESKTOP_PRODUCTIZATION_PLAN.md`](DESKTOP_PRODUCTIZATION_PLAN.md). Этот файл
описывает следующий продуктовый слой: что именно улучшать после пилотной версии.

## Правило начала каждой задачи

Запись задачи в этом файле не означает немедленное изменение кода. Перед каждой
реализацией выполняются отдельные шаги:

1. обсуждаем пользовательский сценарий и ожидаемый результат;
2. определяем состояния интерфейса, ошибки и пограничные случаи;
3. проверяем влияние на локальную БД, backup, лицензирование и разные источники;
4. составляем короткий технический план и критерии приёмки;
5. только после согласования приступаем к реализации и сборке.

Если при обсуждении задача окажется преждевременной, она переносится в
[`FUTURE_PRODUCT_PLAN.md`](FUTURE_PRODUCT_PLAN.md), а не реализуется частично.

## STAB-1. Устойчивый запуск Playwright и восстановление компонентов поиска

**Статус:** реализовано в коде, требуется проверка новой macOS- и Windows-сборки.
**Приоритет:** первый.
**Цель:** длительная работа, сон и очистка временных файлов не должны лишать
приложение возможности запускать поиск; повреждение компонентов должно иметь
понятный исход и путь восстановления.

### Подтверждённая проблема и границы вывода

При диагностике 9 сентября в каталоге работающего macOS backend отсутствовал
`playwright/driver/package/cli.js`; журнал содержал `Connection closed while
reading from the driver`, а отчёт — вторичный `AttributeError` про `_playwright`.
Отсутствие файлов подтверждено. Кто именно их удалил — системная очистка,
сторонняя утилита или другой процесс — по имеющимся журналам не установлено.

В `scripts/build_desktop_sidecar.py` постоянная распаковка включена только для
Windows. macOS использует временный `onefile_*`. Скрипт
`scripts/prepare_desktop_playwright_driver.py` выносит в ресурсы только Node.js;
JS-пакет драйвера остаётся в распакованном backend. Поэтому наличие Node.js и
работающий `/api/health` не доказывают готовность поиска.

### Предлагаемая реализация

1. Проверить на закреплённой версии Nuitka поведение постоянной распаковки:
   восстановление отсутствующего/повреждённого файла при новом запуске,
   блокировки, подпись macOS и запуск из `.app`. Использовать небольшой
   воспроизводимый пример до полной дорогостоящей сборки.
2. Для macOS убрать рабочие компоненты из системного временного каталога.
   Основной вариант — штатная постоянная распаковка Nuitka в отдельный каталог
   runtime под `Application Support/com.searchcar.desktop`, с версией, целевой
   архитектурой и отпечатком сборки. Точный способ передачи пути из Tauri или
   задания поддерживаемой спецификации Nuitka проверить на первом шаге.
   Не считать обычный `Library/Caches` гарантированно постоянным хранилищем.
   Если этот вариант не проходит проверку подписи/восстановления, выбрать
   `standalone` backend внутри `.app` и пересчитать объём упаковочных изменений.
   Не поддерживать два новых production-варианта одновременно.
3. Изолировать сборки с одинаковым номером версии: отпечаток должен учитывать
   код, зависимости, параметры упаковки и платформу. Не перезаписывать файлы
   работающей сборки. Существующие Windows-флаги консоли и сжатия оставить
   платформенными; общую логику идентификации и проверки переиспользовать.
4. В общем пути запуска браузера проверять Node.js, точку входа `cli.js`,
   Chromium и совместимость манифеста с упакованным Playwright. Полную проверку
   целостности делать при подготовке runtime; перед поиском — короткую проверку
   необходимых файлов. Наличие `cli.js` само по себе не доказывает целостность
   всего драйвера: нужен ограниченный по времени пробный запуск и обработка
   его завершения. Общая проверка применяется к worker и `browser-check`.
5. При неисправности выдавать отдельный код компонента поиска и понятное
   сообщение с действиями `Перезапустить приложение` и `Создать отчёт`.
   Подготовить безопасный перезапуск: зафиксировать частичный результат,
   завершить процессы, восстановить runtime из установленного пакета и только
   затем разрешить новый поиск. Не скачивать исполняемые файлы из произвольных
   источников и не устраивать бесконечный цикл перезапусков.
6. В журнал сохранять этап запуска, версию/отпечаток runtime, относительный путь
   отсутствующего компонента, код выхода и ограниченный stderr дочернего
   процесса с очисткой секретов. Сейчас Tauri читает события sidecar, но не
   сохраняет их stdout/stderr; учесть это в диагностике первопричины.
7. Служебную распаковку исключить из переносимых backup. Для старых runtime
   предусмотреть ограниченное хранение и безопасную очистку только собственных
   неиспользуемых каталогов; не удалять текущую сборку, базу или каталог лицензии.

### Пользовательское поведение и пограничные случаи

- При восстановлении показывать `Подготавливаем компоненты поиска…` и конечную
  ошибку по таймауту; интерфейс не должен бесконечно ждать.
- После сбоя текущий запуск остаётся частичным/неуспешным, а не успешным с нулём
  изменений. Сохранённые машины, история и пользовательские действия остаются.
- Ошибки сайта, CAPTCHA и отсутствие сети не запускают восстановление runtime.
- Если каталог недоступен для записи или диск заполнен, сообщить об этом прямо.
- Обновление приложения и восстановление компонентов взаимоисключающие;
  планировщик не запускает второй поиск во время восстановления.
- Защита рассчитана на очистку временных файлов и штатное восстановление.
  Произвольное удаление установленного приложения нельзя предотвратить кодом.

### Проверки и критерии приёмки

- Регрессионный тест параметров сборки различает macOS, Windows и diagnostic
  standalone; изменение отпечатка не затрагивает работающую версию.
- На изолированной копии runtime моделировать отсутствие `cli.js`, вложенного
  JS-файла и повреждение компонента; проверить диагностику и восстановление.
  Не очищать общий системный temp и не повреждать установленную рабочую копию.
- Проверить два запуска подряд, сон/пробуждение, отмену, работу после нескольких
  дней, обновление со старой версии и запуск на Windows без новой консоли.
- Проверить готовую подписанную `.app`, а не только бинарник до упаковки.
  В CI добавить короткий тест к единственной production-сборке; не включать
  вторую полную diagnostic-компиляцию и не увеличивать облачный кеш ради теста.

**Готово, когда:** очистка тестового временного каталога не ломает поиск;
повреждение runtime даёт понятную ошибку и проверяемое восстановление;
повторный поиск работает без потери данных. Номер релиза выбрать по актуальной
версии перед выпуском, не фиксировать заранее `0.1.2`.

**Открытые вопросы пользователю перед реализацией:**

- При необходимости восстановления допустим один автоматический перезапуск
  приложения или всегда показывать кнопку подтверждения? Рекомендация для
  первой версии — подтверждение с предупреждением о прерывании поиска.
- После восстановления повторить прерванный поиск один раз автоматически или
  ждать ручного запуска/следующего расписания? Рекомендация — явная кнопка
  `Повторить поиск`, без незаметных повторов.

**Технические вопросы, которые решает разработчик проверками:** поддерживаемый
путь распаковки, восстановление Nuitka, совместимость подписи и очистка старых
версий. Пользователю не нужно выбирать внутренний формат упаковки.

### Реализация 21 сентября

- `cli.js` и весь JavaScript-пакет Playwright теперь поставляются внутри
  `playwright-driver` как ресурсы Tauri вместе с Node.js. Backend проверяет
  их путь, размер и SHA-256, затем направляет Playwright на этот ресурс, а не
  на копию внутри временной распаковки Nuitka.
- Начиная с новой сборки, onefile backend использует версионированный cache
  Nuitka также на macOS. Это снижает риск исчезновения остальных файлов
  распакованного backend и не меняет Windows-настройки консоли/сжатия.
- Сбой запуска драйвера теперь сохраняется как
  `PLAYWRIGHT_RUNTIME_UNAVAILABLE`, а интерфейс предлагает перезапустить
  приложение, вместо технического `ATTRIBUTEERROR`.
- Автотесты проверяют отсутствие `cli.js`, целостность манифеста и
  преобразование сбоя driver в понятный код. Отдельно проверен фактический
  запуск Playwright через подготовленную ресурсную папку.

Перед выпуском остаётся собрать обе платформы, убедиться, что в ресурсах
присутствует `playwright-driver/package/cli.js`, и выполнить ручной поиск
после длительного открытого приложения. Автоматически перезапускать приложение
или повторять прерванный поиск в этой задаче не будем: это требует отдельного
пользовательского сценария и не нужно для устранения первопричины.

## LIVE-1. Результаты в истории сразу после обработки автомобиля

**Статус:** реализовано. **Зависимость:** STAB-1.
**Цель:** пользователь начинает работать с готовыми автомобилями, пока
остальная часть поиска продолжается.

### Текущее поведение

`backend/app/worker.py` сохраняет машины по ходу обработки. Результат сразу
попадает в текущий отчёт запуска; интерфейс получает SSE-сигнал и перечитывает
`/api/scans`. Опрос раз в 30 секунд остаётся только запасным механизмом на
случай переподключения.

### Поведение первой версии

- С начала запуска открывается текущий отчёт с отметкой `Поиск продолжается`.
  Пока готовых данных нет: `Пока нет готовых результатов`, а не `Все объявления
  без изменений`. Предыдущий отчёт остаётся доступным в истории.
- После фиксации машины и события в БД результат появляется при ближайшем
  обновлении интерфейса — ориентировочно в течение двух секунд при отзывчивом
  локальном API. Неподтверждённые изменения цены не публикуются как факт.
- Карточку можно открыть, добавить в избранное, оценить и прокомментировать.
  Последующее сохранение worker не перезаписывает эти пользовательские поля.
- Показываются текущий проект, этап, число обработанных машин, изменений и
  ошибок. До окончания сбора выдачи итоговое количество может быть неизвестно.
- Обновление списка сохраняет фильтры, выделение, прокрутку и открытую карточку.
  Предлагается добавлять поступающие строки в конец; при иной сортировке
  использовать индикатор новых результатов, чтобы строки не прыгали под курсором.
- Ошибки также появляются по ходу поиска и содержат ссылку на машину, если она
  известна. Завершение проекта и всего запуска сохраняет один отчёт без дублей.

### Технические шаги

1. Разделить публикацию промежуточных результатов и завершение проекта.
   Промежуточная публикация не очищает `current_project_id` и не выставляет
   проекту `SUCCEEDED`.
2. Проверить границы транзакций `upsert_detail` и сохранения наблюдений.
   Машина, событие и соответствующая строка отчёта должны сохраняться
   согласованно: аварийное завершение между commit не теряет историю события.
   Публиковать результат из сохранённых данных, не из незавершённого разбора.
3. Для первой версии переиспользовать текущий отчёт и SSE-сигнал. Сигнал не
   содержит данные машины: он только запускает перечитывание `/api/scans`,
   поэтому API остаётся единственным источником истины. WebSocket и отдельный
   сервер не нужны.
4. Устойчиво идентифицировать строки по запуску, машине и наблюдению проекта;
   совместить с существующей дедупликацией пересекающихся проектов. Финальная
   сводка и видимая история должны совпадать с уже опубликованными результатами.
5. Обновить главный отчёт и подробности запуска, восстановление интерфейса после
   закрытия окна и обработку отмены/сна/ошибки. Уже зафиксированные результаты
   остаются доступными после аварийного завершения процесса.
6. Проверять отмену, удаление проекта и отключение отслеживания при сохранении.
   Исчезновение из выдачи определять только после полного успешного обхода;
   неполный запуск не создаёт ложные события отсутствия или продажи.

**Граница первой версии:** порядок обхода страниц остаётся прежним — сначала
сбор выдачи, затем карточки. Чтение «страница → её карточки → следующая страница»
может дополнительно сократить время до первого результата, но требует отдельной
проверки пагинации и динамической выдачи; не включать молча в эту задачу.
Нативные уведомления остаются задачей 7, отдельный раздел `Изменения` — задачей 6.

### Проверки и критерии приёмки

- Тест с двумя машинами: первая сохранена и доступна через API/UI, пока чтение
  второй намеренно задержано; ни один проект ещё не завершён.
- Повтор, пересекающиеся проекты и финализация не создают двойных строк.
- Отмена, сон и авария после первого результата сохраняют его в истории.
- Открытая карточка, комментарий, избранное и прокрутка не теряются при обновлении.
- Большой отчёт не замедляет заметно поиск и не блокирует интерфейс на обеих ОС.

**Готово, когда:** пользователь видит и обрабатывает первую готовую машину до
завершения проекта; итоговая история согласована с промежуточной.

### Реализация 22 сентября

- Добавлен локальный SSE-канал `/api/events`. Он изолирован по владельцу и
  передаёт только coalesced-сигнал `scan_changed`, без данных автомобиля.
- Worker сохраняет промежуточный отчёт, ошибки и сводку в той же транзакции,
  после которой публикуется сигнал. `current_project_id` сохраняется до
  фактического окончания проекта.
- Главный экран показывает активный отчёт сразу: до первого изменения —
  понятное `Ищу…`, а не ошибочное `Все объявления без изменений`.
- Сохранён fallback-опрос `/api/scans` раз в 30 секунд. Браузер сам
  переподключает SSE; новых сервисов и зависимостей не добавлено.

**Открытые вопросы пользователю перед реализацией:**

- Показываем только новые/изменившиеся машины или также проверенные без изменений?
  Рекомендация — изменения по умолчанию; `Все обработанные` отдельным режимом,
  если он действительно нужен, с сохранением наблюдений без изменений.
- Новые строки добавлять в конец автоматически или показывать кнопку
  `Показать ещё N результатов` при просмотре середины списка?
- Нужно ли уже в первой версии обрабатывать карточки до завершения сбора всех
  страниц? Рекомендация — выделить это следующим небольшим этапом после замеров.

## PRICE-1. Диапазон цен проекта перед поиском на Encar

**Статус:** реализовано в коде, требуется проверка новой macOS- и Windows-сборки. **Зависимость:** LIVE-1.
**Цель:** задать бюджет в SearchCar и искать на сайте по этим условиям при каждом
ручном или запланированном запуске. Это отдельная функция от локальных фильтров
уже сохранённых автомобилей в задаче 8.

### Сценарий и модель настроек

1. Пользователь вставляет ссылку выдачи при создании/редактировании проекта.
   Приложение извлекает распознанный диапазон цены и показывает его в форме.
2. Пользователь задаёт `Цена от` / `Цена до`. Валюта явно указана: KRW;
   автоконвертация валют в первой версии не нужна. В БД хранятся целые воны.
3. Предусмотреть явные режимы: `Как в ссылке`, `Мой диапазон`, `Без ограничения
   цены`. Пустые поля не должны неоднозначно означать и наследование, и удаление
   фильтра. Остальные условия ссылки сохраняются во всех режимах.
4. Один край диапазона может отсутствовать. Значения неотрицательные, минимум
   не больше максимума; проверить фактический шаг цены и предельные значения
   Encar. Единицы сайта (если отличаются от KRW) конвертируются без скрытого
   округления. Ошибку показывать рядом с полем до сохранения.
5. На проекте показывать применяемый диапазон. Изменения формы влияют на новые
   запуски; активный запуск использует неизменный снимок условий.

### Как применять на сайте

- Перед реализацией проверить актуальную выдачу Encar на примерах: без цены,
  только нижняя граница, только верхняя, обе границы, пустая выдача. Зафиксировать
  очищенные URL/fixtures и фактические единицы. Не придумывать имена параметров.
- Предпочесть формирование корректного URL, если сайт сохраняет в нём диапазон.
  Иначе заполнить поля на странице через Playwright и дождаться применения.
  Выбрать один основной способ по результатам проверки, не поддерживать два
  параллельных механизма без необходимости.
- Подтверждать фактически применённые условия, в том числе на следующих страницах.
  При сбросе/неприменении диапазона остановить поиск с понятной ошибкой.
  Пустая выдача считается корректным результатом только после проверки фильтра.
- Проверку/построение условий вынести в небольшую функцию Encar, совместимую с
  будущим адаптером задачи 17; весь рефакторинг источников сейчас не требуется.

### Данные, история и старые проекты

- Добавить режим цены, границы и ревизию условий в модель проекта, схемы
  создания/изменения API и миграции. Существующие проекты получают `Как в ссылке`
  и сохраняют прежнее поведение; обновить backup/restore и проверить перенос ОС.
- В запуске сохранять снимок исходных/эффективных условий и ревизию проекта
  при постановке в очередь. Повтор использует тот же снимок; новый запуск —
  актуальные настройки. Для старых записей без снимка нужна совместимая загрузка.
- Изменение цены создаёт новую область поиска. Не сравнивать её отсутствие
  машин с предыдущей как продажу/исчезновение: первая полная успешная проверка
  новой ревизии устанавливает новую базу сравнения. Ошибки, отмена и режим одной
  страницы не устанавливают полный базовый набор. Согласовать правило первого
  точного поиска при изменении диапазона.
- Не удалять старые машины, заметки, избранное или историю. Соответствие текущему
  диапазону — свойство наблюдения проекта, не глобальный статус автомобиля.
  Неизвестная или старая цена не является доказательством выхода за диапазон.
- Проверить `_missing_cars`: он не должен автоматически перечитывать все машины
  за пределами нового бюджета и тем самым отменять экономию поиска. Поведение
  их отдельного отслеживания согласовать до реализации.
- Проверить существующую уникальность `(owner_id, search_url)`: проекты с одной
  ссылкой и разными бюджетами сейчас конфликтуют. Решение о разрешении таких
  проектов принять явно, вместе с миграцией и проверкой дубликатов.

### Проверки и критерии приёмки

- Цена из URL, override, явное снятие фильтра, одна граница, неверный диапазон,
  неподдерживаемый формат ссылки; все остальные фильтры сохраняются.
- Ручной запуск и расписание используют одинаковые эффективные условия;
  редактирование во время очереди/поиска не смешивает разные диапазоны.
- Пагинация сохраняет цену; неприменённый фильтр не превращается в поиск без
  ограничений. Точные граничные значения включаются по согласованным правилам.
- Сужение и расширение бюджета, пустая выдача, неизвестная цена, пересечения
  проектов и избранное не создают ложных продаж и не уничтожают историю.
- Старый backup восстанавливается с прежними условиями, новый сохраняет настройки
  на macOS и Windows. Фактическую цену карточки не подменять границей фильтра.

**Готово, когда:** диапазон из приложения подтверждён на Encar для всего обхода,
история показывает условия запуска, а смена бюджета не искажает статусы машин.

### Реализация 22 сентября

- В форме проекта добавлены режимы `Как в ссылке Encar` и `Мой диапазон`.
  В режиме диапазона есть прямой ввод сумм и два
  ползунка от 0 до 100 000 000 KRW; ползунки работают с шагом 1 000 000 KRW,
  прямой ввод принимает шаг 10 000 KRW, который использует Encar.
- Диапазон хранится отдельно от исходной ссылки. Перед поиском приложение
  заменяет существующий `Price.range(...)` или добавляет его при отсутствии,
  сохраняя остальные условия и пагинацию.
- Смена ссылки или диапазона создаёт новую ревизию. Следующий запуск становится
  точным и проходит все страницы; до его успешного завершения прежние машины
  не проверяются как пропавшие и не получают статус продажи.
- Добавлены миграции PostgreSQL и локальной SQLite-базы, API-валидация и тесты
  для замены, добавления диапазона и перехода на следующую страницу.

**Открытые вопросы пользователю перед реализацией:**

- Вводить сумму в полных вонах (`25 000 000`) или в миллионах (`25`)?
  Рекомендация — полные воны с разделителями разрядов и подписью KRW.
- Подходит ли выбор `Как в ссылке / Мой диапазон`?
  При вставке другой ссылки рекомендуем сохранять явно заданный диапазон и
  показывать, что он имеет приоритет, а не сбрасывать его незаметно.
- Продолжать проверять ранее найденные машины вне нового диапазона: все,
  только избранные или ни одну автоматически? Рекомендация — только избранные,
  отдельным обозначенным этапом; остальные остаются в истории.
- Разрешить несколько проектов с одной ссылкой, но разным бюджетом?
  Рекомендация — разрешить разные эффективные условия.
- После изменения диапазона выполнять один точный поиск по всем страницам,
  затем возвращаться к выбранному режиму? Рекомендация — да, с пояснением.

## 1. Надёжное завершение фоновых операций

**Цель:** ни одна кнопка не должна оставаться бесконечно заблокированной после
проверки обновления, создания отчёта, backup или другой фоновой операции.

Ожидаемое поведение:

- операция всегда переходит в одно из конечных состояний: выполнена, отменена
  или завершена ошибкой;
- у каждой сетевой и межпроцессной операции есть разумный timeout;
- временная недоступность локального backend не уничтожает поток, который
  обслуживает последующие запросы;
- после ошибки кнопка снова доступна, а пользователь видит действия `Повторить`
  и, где уместно, `Создать отчёт`;
- закрытие и повторное открытие окна восстанавливает фактическое состояние, а
  не старую надпись `Выполняется`;
- системный tray, ручная кнопка и автоматический запуск используют согласованное
  состояние одной операции.

Текущий найденный дефект проверки обновлений уже исправляется локально:
обработчик переживает кратковременную потерю связи с backend, а запрос к updater
ограничен по времени. Перед завершением задачи нужны commit, desktop-сборка и
проверка сценариев `обновление найдено`, `обновлений нет`, `нет сети`,
`backend временно недоступен` и `повтор после ошибки`.

**Критерий готовности:** после любого исхода интерфейс становится доступен без
перезапуска приложения и показывает правдивый результат.

## 3. Понятные статусы и свежесть данных автомобиля

**Цель:** пользователь должен понимать, где машина была обнаружена и какие её
данные действительно удалось проверить.

Одна метка не сможет честно описать оба аспекта, поэтому предлагаются два
независимых уровня.

### Статус объявления

- `В продаже` — машина найдена в последнем успешном поиске проекта;
- `Не найдено в выдаче` — машина отсутствовала в последнем полном поиске по всем
  страницам; это не означает, что она продана;
- `Продано` — страница самой машины явно подтвердила продажу;
- `Снова в продаже` — ранее отсутствовавшая машина снова появилась.

Отдельный статус `Недоступно` добавляется только после обсуждения надёжного
признака. Ошибка загрузки страницы сама по себе не должна менять автомобиль на
`Продано` или `Недоступно`.

### Качество проверки данных

- `Проверено` — подробная страница успешно прочитана;
- `Обновлено по выдаче` — быстрый поиск увидел машину и обновил доступные в
  выдаче поля, но подробную страницу не открывал;
- `Частично проверено` — машина найдена, однако подробности прочитаны не
  полностью; последние корректные значения сохранены;
- `Требует проверки` — критичные сведения ещё ни разу не были успешно получены
  либо ошибка повторяется.

Рядом показываются две даты: `В выдаче: дата и время` и `Подробности проверены:
дата и время`. Порог, после которого данные считаются устаревшими, обсуждается
перед реализацией и должен учитывать выбранный интервал планировщика.

### Где показывать

- в карточке автомобиля — компактный статус объявления, время свежести и только
  значимое предупреждение о неполных данных;
- в подробной карточке — обе даты, полный статус проверки и последняя понятная
  причина ошибки;
- в проекте — сводка количества машин по состояниям;
- в отчёте запуска — результат проверки каждой проблемной машины;
- в будущем разделе `Изменения` — только фактические события, а не повтор всех
  текущих статусов.

**Нужно:** расширить сохранение результатов наблюдения, не смешивая общий статус
машины с её присутствием в конкретном проекте; обновить API, карточки, отчёты и
миграцию SQLite.

**Критерий готовности:** по любой карточке можно понять, когда машина была видна
в поиске, когда открывалась её страница и какие значения могли устареть.

## 6. Отдельный раздел `Изменения`

**Цель:** собрать все значимые изменения из проектов в одну рабочую ленту.

В боковом меню появляется самостоятельный пункт `Изменения`, расположенный на
одном уровне с `Проекты`, `Запуски` и `Настройки`. Возле него отображается число
непросмотренных событий.

Первая версия ленты содержит:

- новые машины;
- повышение и снижение цены;
- подтверждённую продажу;
- исчезновение из полной выдачи и повторное появление;
- значимые изменения характеристик, если подробная страница была перечитана.

События можно фильтровать по проекту, типу, периоду, избранному и состоянию
`Непросмотренные`. Нажатие открывает карточку машины. Событие имеет собственный
признак просмотра: просмотр машины раньше не скрывает новое снижение её цены.
Повторяющиеся изменения одной машины в одном запуске объединяются в одну запись.

`Запуски` остаются технической историей того, когда и как выполнялся поиск.
`Изменения` отвечают на пользовательский вопрос: что нового произошло с
машинами.

**Нужно:** использовать существующие события автомобилей, добавить устойчивый
идентификатор события, состояние просмотра и API ленты; затем добавить экран и
счётчик в навигацию.

**Критерий готовности:** после поиска пользователь открывает один раздел и видит
все новые значимые события без просмотра каждого отчёта запуска.

## 7. Уведомления об изменении цены избранных машин во время поиска

**Цель:** сообщать о цене важной машины сразу после её успешного обновления, не
дожидаясь завершения поиска остальных автомобилей.

Это возможно в текущей локальной архитектуре. После сохранения и фиксации в БД
события цены backend помещает его в локальную очередь уведомлений. Desktop shell
забирает событие и показывает нативное уведомление Windows или macOS, пока
worker продолжает поиск.

Правила первой версии:

- уведомления отправляются только для машин, находившихся в избранном на момент
  изменения;
- показываются и снижение, и повышение цены;
- первая полученная цена не считается изменением;
- уведомление содержит машину, старую и новую цену, абсолютную и процентную
  разницу;
- нажатие открывает нужную карточку автомобиля;
- один ценовой event отправляется один раз, включая перезапуск приложения;
- если ОС запретила уведомления, событие всё равно остаётся в разделе
  `Изменения`, а в настройках показывается понятное состояние разрешения;
- при большом числе одновременных изменений применяется короткое объединение,
  чтобы не показать десятки окон подряд. Точный порог обсуждается перед
  реализацией.

Перед реализацией отдельно решаем, нужны ли пользователю минимальная сумма или
процент изменения и тихие часы. Основной сценарий не требует Telegram, сервера
уведомлений или платной инфраструктуры.

**Нужно:** нативные разрешения и уведомления Tauri, локальная очередь на основе
сохранённых событий, защита от дублей и переход из уведомления к карточке.

**Критерий готовности:** во время длинного поиска изменение цены избранной
машины появляется сразу после сохранения этой машины и не повторяется без нового
изменения цены.

## 8. Расширенные фильтры и сохранённые подборки

**Цель:** быстро сужать большую выдачу и возвращаться к часто используемому
набору условий.

Здесь фильтруются уже сохранённые данные внутри приложения. Применение диапазона
цен непосредственно на Encar до сбора машин реализуется раньше в PRICE-1;
настройки поискового бюджета и временный фильтр просмотра не должны менять друг
друга. Формат цены и подписи переиспользуются из PRICE-1.

Планируемые фильтры: цена, год, пробег, состояние объявления, качество проверки,
дата появления, непросмотренные, избранные, оценка пользователя, ключевые опции
и состояние автомобиля. Несколько фильтров применяются одновременно по
понятному правилу `И`, а выбранные значения внутри одного поля — по правилу,
согласованному для этого поля.

Пользователь сможет сохранить текущую комбинацию под своим названием, например
`До 25 млн, полный привод`, и применить её к проекту. Для каждого фильтра нужно
различать `Нет`, `Есть` и `Не удалось определить`: неизвестное значение нельзя
считать отсутствующим.

Перед реализацией определяем, какие фильтры общие для всех источников, а какие
доступны только для конкретного сайта. Сохранённая подборка должна переживать
переименование проекта и корректно сообщать об исчезнувшем поле источника.

**Нужно:** схема сохранённых наборов, единая модель фильтров API/UI и счётчик
результатов до применения тяжёлых условий.

**Критерий готовности:** пользователь сохраняет комбинацию, повторно применяет
её и получает тот же результат на тех же данных.

## 5. Автоматические локальные резервные копии

**Цель:** защищать проекты, историю и заметки, даже если пользователь забывает
нажимать ручной backup.

Первая версия использует уже существующий проверяемый формат backup. Пользователь
выбирает папку, периодичность и число сохраняемых копий. Интерфейс показывает
дату последней успешной копии, следующую попытку, занятое место и последнюю
ошибку. Старые автоматические копии удаляются только в выбранной приложением
подпапке и только по установленному лимиту.

Копирование не начинается во время восстановления, обновления приложения или
операции, которая уже блокирует базу. Пропущенная копия выполняется один раз при
следующем подходящем запуске. Ручной backup остаётся доступен независимо от
расписания.

Перед реализацией нужно решить безопасные значения по умолчанию. Пока отдельная
папка не выбрана, приложение не должно создавать ощущение защиты от поломки
диска: копия в каталоге приложения спасает от повреждения данных, но не от
потери самого накопителя.

**Нужно:** расписание, системный выбор папки, retention, проверка созданного
архива и отображение состояния в `Настройки → Резервные копии`.

**Критерий готовности:** приложение автоматически создаёт и проверяет копию,
соблюдает лимит хранения и позволяет восстановить её на тестовой установке.

## Выбор удаления локальных данных при деинсталляции Windows

**Цель:** при удалении SearchCar через настройки Windows пользователь сам
выбирает, сохранить локальные данные или удалить их полностью.

По умолчанию опция `Удалить все локальные данные SearchCar` выключена: обычная
переустановка не должна случайно удалить проекты и историю. При её выборе
деинсталлятор удаляет локальную базу, проекты, историю, настройки, журналы, кэш
и сохранённые на компьютере данные лицензии. Перед подтверждением показывается
предупреждение о необратимости и совет создать резервную копию.

Серверные записи клиента и лицензии не удаляются. При тихом удалении данные
сохраняются, если не передан отдельный явный флаг очистки.

Перед реализацией нужно:

- определить все каталоги и системные хранилища SearchCar на Windows;
- встроить выбор в NSIS-деинсталлятор;
- согласовать остановку активного поиска и других процессов;
- проверить повторную установку после обоих вариантов удаления.

**Критерий готовности:** пользователь понимает последствия выбора, может
безопасно переустановить приложение с сохранёнными данными или осознанно удалить
все локальные сведения без изменения серверной лицензии.

## 9. Сравнение выбранных автомобилей

**Цель:** сравнить основные кандидаты без переключения между карточками.

Пользователь выбирает от двух до четырёх машин из одного или разных проектов и
открывает экран сравнения. Столбцы — автомобили, строки — цена, изменение цены,
год, пробег, двигатель, привод, коробка, ключевые опции, сведения о состоянии,
пользовательская оценка и краткая заметка.

Нужны режимы `Все характеристики` и `Только различия`. Неизвестные данные
показываются как `Не удалось определить`, а не как отсутствие опции. Для каждой
машины доступны переход в карточку и на исходное объявление. Выбранное сравнение
можно очистить одним действием; постоянное хранение наборов сравнения в первой
версии не обязательно и обсуждается отдельно.

Для разных источников сначала показываются общие нормализованные поля, затем —
отдельный блок специфичных характеристик каждого источника. Значения с разными
единицами должны быть приведены к общей форме.

**Нужно:** состояние выбора машин, нормализованная таблица сравнения и адаптивное
представление для небольшого окна.

**Критерий готовности:** различия между четырьмя машинами можно увидеть на одном
экране без потери отметок о неизвестных данных.

## 12. Экспорт подборки

**Цель:** передать клиенту или коллеге понятный результат без установки
SearchCar.

Первая версия формирует:

- `CSV` для дальнейшей работы в Excel или Google Sheets;
- автономный `HTML` для удобного просмотра и печати в PDF средствами браузера.

Экспортировать можно выбранные машины либо текущий отфильтрованный список. В
файл входят название проекта, характеристики, цена и её изменение, состояние,
дата последней проверки и безопасная ссылка на исходное объявление. Комментарии
и оценки включаются отдельным явным переключателем. Изображения также должны
быть опцией, потому что они значительно увеличивают размер файла.

Документ содержит дату формирования и предупреждение, что сведения отражают
последнюю локальную проверку. Секреты, лицензия, технические логи и внутренние
пути не экспортируются.

Перед реализацией согласуем состав столбцов, вид HTML и поведение для
непроверенных значений. Отдельный генератор PDF пока не требуется.

**Нужно:** общий объект экспортируемой подборки, безопасные шаблоны CSV/HTML,
системный выбор папки и проверка открытия файлов на Windows/macOS.

**Критерий готовности:** получатель открывает экспорт без SearchCar и понимает,
какие сведения актуальны и откуда перейти к объявлению.

## 13. Понятные выводы из истории цены

**Цель:** дополнить существующий график краткими фактами, которые не нужно
высчитывать вручную.

На карточке показываются:

- первая замеченная и текущая цена;
- общая разница в валюте и процентах;
- минимальная и максимальная замеченная цена;
- число повышений и снижений;
- длительность локального наблюдения;
- дата последнего изменения цены.

Формулировка должна быть `Наблюдаем 20 дней`, если реальная дата публикации
объявления неизвестна. Несколько одинаковых наблюдений не создают ложных
изменений, а пропуски проверки не соединяются выдуманной непрерывной линией.

Перед реализацией обсуждаем минимальное число точек для каждого вывода и
отображение повторной публикации машины.

**Нужно:** расчёты по существующей истории, компактный блок над графиком и тесты
на повышение, снижение, одинаковую цену и один замер.

**Критерий готовности:** все показанные числа воспроизводятся из сохранённой
истории и не заявляют о данных, которых SearchCar не наблюдал.

## 14. Сравнение цены с локальной выборкой

**Цель:** показать положение цены автомобиля среди достаточно похожих машин,
уже собранных SearchCar.

Первая версия не пытается предсказать цену. Она показывает проверяемую
статистику: медиану выборки, отклонение текущей цены, диапазон и число
автомобилей. Группа строится по источнику, модели/поколению, близкому году,
двигателю, приводу и диапазону пробега. Используются только свежие, доступные и
не дублирующиеся объявления.

Если данных мало или характеристики не удалось сопоставить, оценка не
показывается. Формулировка: `На 7% ниже медианы среди 24 похожих машин в вашей
локальной базе`, а не `Выгодная цена на рынке`. Пользователь может открыть
состав выборки и понять, с чем выполнено сравнение.

Перед реализацией отдельно согласуем нормализацию комплектаций, допустимую
свежесть, минимальный размер выборки и диапазоны года/пробега. Начать следует с
простой медианы, без скрытой формулы рейтинга.

**Нужно:** нормализованные характеристики, построитель сопоставимой выборки,
защита от дублей и объяснимый UI.

**Критерий готовности:** оценка воспроизводима по показанной выборке и исчезает,
если данных недостаточно.

## 16. Добавление отдельной машины по ссылке в проект `Вне проекта`

**Цель:** начать наблюдать за конкретным объявлением без создания отдельного
поискового проекта.

Предлагаемый сценарий:

1. пользователь вставляет ссылку в общее поле поиска машины;
2. приложение распознаёт поддерживаемый источник и ищет машину в локальной БД;
3. если машина уже существует, открывается её карточка и предлагается включить
   отслеживание, если оно было выключено;
4. если машины нет, появляется действие `Следить` с названием распознанного
   источника;
5. после подтверждения приложение создаёт или использует системный проект
   `Вне проекта`, загружает карточку и добавляет её туда;
6. следующие ручные и запланированные проверки обновляют эту отдельную машину.

`Вне проекта` должен иметь внутренний системный признак, а не определяться
только по имени. Это исключит конфликт, если пользователь сам создаст или
переименует проект с таким названием. Внутри одного системного проекта могут
быть прямые ссылки на разные автомобили; их нельзя моделировать одним обычным
`search_url` проекта.

Дополнительные правила:

- одна и та же машина не дублируется при повторной вставке ссылки;
- неподдерживаемая или небезопасная ссылка получает понятную ошибку;
- источник сначала проверяется по лицензии;
- проданная или исчезнувшая машина сохраняет историю и остаётся доступной;
- машину можно удалить из `Вне проекта` либо перенести/добавить в обычный
  проект, если она соответствует его выдаче;
- проект можно включать в планировщик целиком, а каждую машину — временно
  отключать от наблюдения;
- поиск по обычному тексту/ID продолжает работать и не смешивается с разбором
  URL.

Перед реализацией согласуем название в интерфейсе, включение проекта в
планировщик по умолчанию и поведение при первой ошибке загрузки.

**Нужно:** таблица прямых наблюдений или эквивалентная модель, системный тип
проекта, распознавание ссылок через source adapter и отдельный job обновления.

**Критерий готовности:** новая валидная ссылка превращается в отслеживаемую
машину, повторная ссылка не создаёт копию, а планировщик обновляет её независимо
от поисковой выдачи.

## 17. Заменяемые алгоритмы для разных сайтов

**Цель:** добавлять новые автомобильные площадки без копирования всего worker и
без разрастания условий `если Encar / если другой сайт` по приложению.

Каждый источник получает отдельный адаптер с единым контрактом:

- определить и проверить URL;
- привести URL к каноническому виду;
- извлечь идентификатор объявления;
- пройти страницы поисковой выдачи;
- прочитать краткую строку выдачи;
- открыть и прочитать подробную страницу;
- определить продажу/недоступность и CAPTCHA;
- вернуть общую нормализованную модель автомобиля;
- объявить поддерживаемые возможности и специфичные поля.

Общий worker отвечает за очередь, отмену, прогресс, транзакции, историю,
повторные попытки и отчёт. Адаптер отвечает только за поведение конкретного
сайта. Реестр выбирает адаптер по ключу источника, URL и разрешению лицензии.

Модель данных должна перейти от `canonical_encar_id` к паре
`source + source_listing_id`, сохранив обратную совместимость и историю Encar.
Общие поля хранятся нормализованно, исходные и специфичные сведения — отдельно.
Экран проекта и фильтры ориентируются на возможности адаптера и не показывают
неподдерживаемую функцию как ошибку.

Реализация выполняется в два этапа:

1. вынести существующий Encar в первый адаптер без изменения поведения и
   подтвердить это fixture/regression-тестами;
2. только затем выбрать второй источник и реализовать его адаптер.

Для каждого источника нужны отдельные очищенные fixtures поиска, карточки,
продажи, неполной страницы и блокировки. В админке уже предусмотрено включение
источников для лицензии; клиент проверяет entitlement перед постановкой job.

Перед реализацией нужно провести отдельный разбор текущих границ parser/scanner,
согласовать контракт адаптера, миграцию БД и первый дополнительный сайт. Также
проверяется возможность законного и технически устойчивого доступа без
платного API или proxy.

**Критерий готовности первого этапа:** Encar работает через общий контракт без
регрессий. **Критерий второго этапа:** новый источник добавляется отдельным
модулем, а общая очередь и UI не получают источник-специфичных веток.

## Предварительная последовательность реализации

Важность и порядок разработки отличаются из-за зависимостей. Перед стартом
каждой задачи порядок можно изменить после обсуждения.

1. согласовать вопросы STAB-1, исправить устойчивость Playwright, проверить
   восстановление компонентов и готовую macOS-сборку;
2. согласовать вопросы LIVE-1 и публиковать результаты в истории по мере
   сохранения автомобилей;
3. согласовать вопросы PRICE-1 и добавить диапазон цен проекта, применяемый
   на Encar перед поиском;
4. завершить задачу 1 и выпустить проверенное исправление updater;
5. согласовать и реализовать модель статусов из задачи 3;
6. добавить автоматические backup из задачи 5;
7. реализовать события и самостоятельный раздел задачи 6 на основе результатов
   LIVE-1, затем поверх событий добавить нативные уведомления задачи 7;
8. реализовать локальные фильтры задачи 8 и сравнение задачи 9;
9. добавить выводы истории цены задачи 13 и экспорт задачи 12;
10. после накопления качественных данных перейти к локальному сравнению задачи
   14;
11. спроектировать общую часть задач 16 и 17, вынести Encar в адаптер и затем
   добавить наблюдение по прямой ссылке;
12. выбирать второй источник только после стабильности первого адаптера.

Выбор удаления данных в Windows-деинсталляторе остаётся самостоятельной задачей
текущего плана: после первых трёх задач его можно выполнять независимо от ленты
событий. Параллельные машины и проекты остаются в `FUTURE_PRODUCT_PLAN.md`.

## Ограничение стоимости

Все задачи этого документа проектируются без обязательного платного облачного
поиска, AI API, proxy или сервиса аналитики. Поиск, статистика, очередь событий,
уведомления и экспорт работают локально. Cloudflare используется только в
существующих границах лицензирования и управления доступом к источникам.
