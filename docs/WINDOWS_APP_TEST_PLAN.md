# SearchCar Desktop: проверка установленного Windows-приложения

Обновлено 3 ноября 2026 года под исправления выбора браузера, native menu recovery
и пробный обычный сеанс Copart. Это план выполнения,
не отчёт о пройденной приёмке. Прежние PASS относятся только к прежнему кандидату.
Основной backlog остаётся в `docs/MULTISOURCE_IMPLEMENTATION_BACKLOG.md`, раздел MSA-19.

Базовая диагностика добавляет наблюдение за UI/нативным окном и состоянием источника
при сбое, уменьшает повторные успешные HTTP-записи, показывает диапазон/усечение
логов в manifest. Он **не исправляет и не обходит** блокировки Copart или паузу
WebView. Успешные и неуспешные поиски проверять заново, а не ожидать победы заранее.
Ранее CSS 401/403 перестал блокировать партию при реально прочитанной выдаче;
реальный отказ документа/скрипта, CAPTCHA и 429 по-прежнему не игнорируются.

## Приоритетная приёмка исправлений от 3 ноября

Сначала этот короткий проход, не все разделы A–L. Успех unit-тестов на Mac
не подтверждает работу нативного Windows hook или доступ живого Copart.

1. Проверить новый SHA/установщик, сохранить backup, подтвердить `source-tests`.
2. **Браузер.** С согласия пользователя назначить Chrome для HTTPS, полностью
   перезапустить SearchCar. Выбор фильтров и поиск одного небольшого IAA-проекта
   должны использовать Chrome. Повторить с Edge. При конфликте старого
   `UserChoice` и `UserChoiceLatest` приложение должно следовать эффективной
   HTTPS-ассоциации Windows, а не старому ключу. Ключи вручную не редактировать.
3. **Меню.** На простое Alt+Space → 45 секунд → Escape; 30 секунд без клика.
   Счётчик/статусы восстанавливаются сами. Повторить дважды; затем отдельно
   проверить сворачивание и уход в другое приложение: фокус не перехватывается.
   В preview ZIP искать `menu-resume` и следующие UI/native события. Отсутствие
   события само по себе не доказывает, что hook не сработал: диагностическая
   отправка также может быть занята. При зависании сохранить ZIP до повтора.
4. **Copart.** Один небольшой A, затем B; только после успеха — общая партия A+B.
   В журнале `mode=windowed-background`: обычный Chrome/Edge с отдельным профилем
   SearchCar стартует и сворачивается. Краткое появление окна возможно; если
   автосворачивание недоступно, виден прежний `MANUAL_MINIMIZE` без перезапуска.
   При штатном запросе проверки восстанавливается та же страница/сеанс, без
   повторного открытия сайта. Затем проверить отмену и следующий маленький поиск.
5. **Отказ сайта.** На первом реальном 403/429 прекратить Copart-проход и сохранить
   support ZIP с точным временем. Никаких серий повторов или удаления профиля.
   Обычный сеанс — эксперимент, не обещание устранить CAPTCHA/отказ сайта.
6. Короткая регрессия: один IAA и один Encar; сохранённые данные/история остаются.

Постоянное восстановление меню не удалять вместе с временной телеметрией.
Установленный Windows smoke и новый Windows compile ещё не выполнены.

## Быстрый маршрут следующего теста

1. A01–A06: проверить новый установщик, сохранить backup **до** теста, пути и данные.
2. L01: подтвердить, что диагностические события действительно записываются.
3. D03/D04 + L02: два маленьких Copart-проекта отдельно и общей партией
   (если их нет, сначала создать по D01/D02).
   При первом сбое — сначала L06, только потом один разрешённый повтор.
4. L03–L05: отдельно обычный простой, Alt+Space и сворачивание; не смешивать их с поиском.
5. E01–E05, F03/F05, G01–G04, J06/J08: IAA/Encar, история, карточки и штатный выход.
6. Передать отчёт с точной последовательностью действий, support zip и, с согласия,
   backup **после** сбоя. Если сбоев нет — всё равно приложить итоговый support zip.

Полный план A–K остаётся ниже. L — приоритетный диагностический проход этой версии.
Проверку с меню во время поиска проводить только после раздельных сценариев.

## 2. Правила безопасности и фиксации результата

1. Сначала только диагностика и проверка. Не исправлять код, не обновлять сервисы,
   не коммитить, не пушить, не выпускать релиз автоматически.
2. Тестировать установленный `.exe`, не заменять его dev-сервером или запуском Python.
   Не удалять приложение, рабочие данные, cookies, кеши и лицензию для «чистоты».
3. До изменений создать штатную резервную копию и сохранить вне каталога установки.
   Если это невозможно — остановить проверки восстановления/удаления/переустановки.
4. Создавать проекты с префиксом `QA-WIN-`. Удалять только явно созданные тестовые объекты.
5. Нужны отдельные разрешения пользователя на: отправку в указанный Telegram-чат,
   включение автоматической отправки/расписания, изменение серверных прав лицензии,
   перенос/отзыв лицензии, восстановление БД, удаление приложения/данных,
   принудительное завершение процесса, изменение системного времени/пояса.
   Согласование плана само по себе эти действия не разрешает.
6. CAPTCHA проходит пользователь. Не обходить её, 403/429, не менять IP/идентификацию
   и не переносить cookies обычного браузера. Не запускать бесконечные повторы.
7. Обычный публичный поиск проверять небольшими выборками: сначала одна страница.
   Не создавать искусственную нагрузку на живые сайты.
8. Коды активации, токены, cookies и секреты не включать в отчёт. Support zip —
   основной материал. Backup содержит пользовательские данные: сохранять локально;
   передавать только с явного согласия и отдельно от публичного отчёта, не вместо zip.
   Диагностические пути могут содержать имя пользователя.
9. Использовать статусы `PASS / FAIL / BLOCKED / NOT RUN / N/A`.
   `BLOCKED` — конкретное внешнее препятствие; `N/A` — функции нет в этом кандидате.
   Не считать ожидаемый отказ сайта успешным поиском. Не считать отсутствие ошибки доказательством результата.

Для каждого теста записывать: ID, время и часовой пояс, шаги, ожидаемое/фактическое,
результат, файл доказательства. При сбое — скриншот, полный код/текст ошибки,
источник/проект, номер запуска, исходная ссылка и support zip сразу после события.
Не повторять сразу весь пакет: сохранить первый сбой, затем один контролируемый повтор.
Пример времени: `2026-11-02 14:03:25 +01:00 (Europe/Warsaw)`; писать время каждого
действия, не только время создания архива. Не менять часы ради совпадения с логами.

Пользователь выбирает cookies/проходит CAPTCHA. Записать время подтверждения и закрытия/скрытия окна. Не нажимать другие команды поиска. | После действия есть прогресс или конкретная конечная ошибка. Снимки при ожидании и после, раскрытые подробности запуска. Для долгого «обновляется» записать изменения на 15/30/60/90-й секунде и наличие ожидания действий; 90 секунд не считать общим дедлайном CAPTCHA/всего поиска. Нет молчаливого успеха с нулём вместо непрочитанной страницы. |
| L06 — пакет первого сбоя | Сначала время/скриншот/полный код в «Запуски» → открыть общие настройки → создать и **сохранить** диагностический ZIP → создать локальный backup после сбоя, если UI позволяет. Лишь затем повтор/перезапуск. Для успеха в следующей попытке сохранить второй ZIP и ID, не перезаписывая первый. | ZIP охватывает событие, backup создан позже него. Сохранить реальные имена файлов и report_id. Если UI завис, записать недоступность экспорта, сделать скриншот; после восстановления экспортировать сразу. Не force-kill и не удалять кеши. Если штатный перезапуск необходим, записать времена и создать ZIP после него с оговоркой о пробеле доказательств. |
| L07 — проверка полноты | В каждом ZIP сверить время сбоя с `logs_oldest_at`/`logs_newest_at`, проверить `logs_truncated`. Сопоставить UI, native и source-события с ручной временной шкалой. | Отсутствие события за пределами диапазона ничего не доказывает. При `logs_truncated=true` указать неполноту; не ждать час до экспорта. Отсутствие `menu-key` не опровергает Alt+Space: Windows может перехватить клавишу. |

Как читать данные, не делая преждевременных выводов:

- `Test diagnostic`: `event=native` — состояние нативного окна; `hidden` здесь
  означает **свёрнуто**, не перекрыто другим окном. UI-события heartbeat/focus/blur/
  visibility/timer-gap отражают WebView. Heartbeat номинально раз в 15 секунд;
  UI-gap сравнивать с native, ручными действиями и последующим восстановлением.
- `lag_ms` — задержка UI-таймера, `native_age_ms` — возраст доставленного UI
  health-сигнала, а не прямое измерение работоспособности backend. Нули/отсутствие
  сигнала не принимать за доказательство здоровья. Числа pending/error queries
  — вспомогательные; один счётчик не устанавливает причину зависания.
- `Test source diagnostic` ожидается при ошибке **чтения источника**, а не при
  каждом успешном поиске, отмене до чтения или падении процесса. Он содержит
  флаги ready/blocked/manual_required/consent_required/document_loaded/observed,
  число строк и последние шесть проблемных ресурсов (status/type/роль/хеш пути).
  `observed=false` — DOM не прочитан; это не доказанное отсутствие CAPTCHA.
- 403 у runtime/polyfills/main важнее для гипотезы загрузки приложения сайта,
  чем у CSS; всё равно сопоставить с кодом ошибки и реально прочитанными строками.
  Не объявлять блокировку устранённой и не игнорировать отказ по одному признаку.
- Успешные HTTP-поллинги семплируются: не ожидать 200 в логе на каждый запрос.
  Эти события не содержат полного URL, cookies, токенов, HTML и текстов JS-ошибок.
  Не компенсировать их отсутствие сбором секретов/сырого трафика.

Если Copart работает: сохранить успешные A/B/партия и ZIP, затем L03/L04.
Не создавать искусственный 403, не требовать source-failure записи при успехе.
Если оба диагностических потока отсутствуют и версия не подтверждена — сначала
решить вопрос кандидата, а не объявлять новый инструмент неработающим.

## 14. Порядок работы и критерий завершения

Первый проход для этой версии: быстрый маршрут и L выше. Далее полный проход
(без опасных изменений): A → B → C01 → D01–04 →
E01–05 → F01/F03/F05 → G01–05 → K01. Сразу остановиться при потере/смешении данных,
отправке не тому получателю, неожиданном лицензионном действии или необратимом сбое.
Остальные независимые безопасные сценарии можно продолжить, явно отделив блокер.

Второй проход: остальные штатные сценарии; H/I — с разрешённым чатом/календарём;
J — с согласованными настройками и возвратом исходных значений.
Третий проход: C02–06 и K02–06 на тестовой лицензии/VM, редкие failure/fixture случаи.

Обязательный минимум для принятия последних исправлений:

- правильный installer/запущенный `.exe`, сохранность старого профиля;
- L01 подтверждает запись обоих потоков; L06/L07 сохраняют пригодные доказательства;
- Copart A/B по одному и в общей партии, с реальным чтением выдачи;
- IAA новый выбор и повтор без наследования фильтров;
- Alt+Space 45 секунд и восстановление без клика;
- Encar не сломан;
- источники из лицензии и пустые категории ведут себя по выданным правам;
- штатное закрытие/отмена не оставляют зависших работ;
- backup создан и сохранён; восстановление отдельно не закрыто, пока не проверено.

План не требует, чтобы ноутбук выполнил все рискованные проверки. Непроверенное
остаётся NOT RUN/BLOCKED и перечисляется в итоговом отчёте. Ни успешный CI, ни
fixtures, ни один хороший Copart-запуск не закрывают всю Windows-приёмку.
Отдельно оценить: (1) удалось ли получить диагностику; (2) работает ли продукт.
Полезный отчёт о воспроизведённом сбое не означает PASS для самого поиска/интерфейса.
Перед публичным релизом — отдельная проверка обычного профиля с диагностикой OFF
по TEST_DIAGNOSTICS.md; текущий preview этого не доказывает.
